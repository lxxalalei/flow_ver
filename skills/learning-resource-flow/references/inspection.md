# Inspection Guidance

Inspect 的语义职责只有一个：**补充会改变当前判断的事实。**

它不是固定流程，也不是为了让每个候选“信息更完整”。

## 1. 什么时候值得 Inspect

典型情况：

- 搜索摘要不足以判断候选是否真的相关；
- 同名、版本、作者、语言等关键事实不清楚；
- 用户明确要求公开访问、无需登录、特定格式或可获取性；
- 需要区分资源本体和 landing page；
- 某个未知事实会直接影响是否推荐或是否下载。

低潜候选、摘要已经足够、用户只是先看看时，不需要额外 Inspect。

## 2. Inspect 后只关心决策事实

重点不是收集一整套后端字段，而是回答当前问题，例如：

- 这是不是真正的目标资源；
- 版本是否正确；
- 当前是否可访问；
- 是否存在用户真正需要的表示/格式；
- 是否有失败或限制会改变推荐。

不要寻找或依赖 fingerprint、digest、inspector version、evidence snapshot 等内部证明字段。

## 3. 与下载的关系

用户尚未准备获取资源时，不要为了“以后可能下载”提前 Inspect 全部候选。

真正进入下载时，执行能力会再次确认当前资源事实，因此前面的 Inspect 只服务于语义决策。

## 4. 临时句柄失效不是重新研究的理由

资源句柄可能来自平台搜索、创作者浏览或外部 URL 导入，本质上只是当前 MCP 进程中的操作句柄。

如果句柄失效，但当前对话仍然知道用户选中的具体资源：

1. 有原 URL时，直接用 URL 重新建立句柄；
2. 有稳定平台标识时，精确重新定位同一资源；
3. 只有标题/作者/平台时，只针对这个资源做最小搜索；
4. 只有连原资源都无法确定时，才重新进入发现阶段。

目标是恢复“已经选中的那个资源”，不是重新执行整个搜索任务。
