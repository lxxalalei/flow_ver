# Retrieval Guidance

本文件补充主 Skill 中多轮检索、候选审查、Inspect 与 ResultSet/Presentation 的必要细节。需求理解、来源选择和 query 设计仍以 `SKILL.md` 为主；这里不再要求模型维护 `SemanticReview / Gap / StopDecision` 形式状态机。

## 1. 多轮检索应围绕用户目标自然推进

每一轮只需要回答四件事：

```text
当前用户真正需要什么
  -> 这一轮最值得搜什么
  -> 真实结果是否有用
  -> 还缺什么，下一轮是否有明显不同的路线能补上
```

继续搜索前必须能具体回答：

1. 当前还缺什么？
2. 下一条 SearchDirection / 来源 / query 为什么比刚才更有机会补上？

如果只能说“可能还有更好的”“还有平台没搜”“has_more=true”，就没有足够理由继续。

普通任务通常 1–3 轮有意义搜索已经足够；用户明确要求全面横向比较时可以更广，但每一轮仍必须扩大真实检索空间或补充新的证据，不做近义词循环。

## 2. SearchDirection 是思考角度，不是新的状态模型

SearchDirection 只表达一个真实学习/资源价值，例如：

- 理解形成原理；
- 观察真实过程；
- 找可打印练习本体；
- 确认某个教材/图书版本；
- 补充可信原始来源；
- 找一个具体文件或资源表示。

它不是 query、platform、resource type，也不需要为了形式完整而固定生成几个。

任务很窄时一个方向足够；宽一些时优先 1–3 个彼此互补方向。不要恢复 legacy 中“每个平台先生成多条 query”的前置扩散。

## 3. 首轮 Search 与后续补搜

当前 MCP 接口仍要求少量 ResultSet lineage 操作：

- 新 Flow 首个成功 `resource_search` 使用 `mode=replace`；
- 同一目标后续补搜使用 `mode=extend`，并传当前 MCP 返回的 `base_result_set_id`；
- ResultSet 是不可变快照，跨轮复制、合并、去重由 MCP 完成，Skill 不手工拼接候选；
- 当前 ResultSet/flow 不确定时，先用 `resource_flow_status` 恢复，不从聊天文本猜 ID。

这只是 Tool choreography。不要围绕 `replace/extend/base_result_set_id` 设计语义，也不要向用户解释这些内部概念。

如果未来 MCP 把 lineage 完全内部化，本段应随公共 Tool 契约删除，而不是继续作为 Skill 永久知识。

## 4. `limit`、ResultSet 与 `has_more`

`resource_search.limit` 控制每个平台 Adapter 的返回预算，不是合并后 ResultSet 的全局容量。MCP 合并、去重后的实际 `candidates` 才是当前可以审查、Inspect 和展示的候选事实。

不要：

- 因为前一个平台先返回很多结果，就认为后面的平台应该被全局截断；
- 在 Skill 里静默截掉 ResultSet 来“控制上下文”；
- 把 `platform_runs` 的 candidate count 当成候选已经进入 ResultSet；
- 因为 `has_more=true` 自动翻页或自动继续搜索。

Presentation 可以只展示少量高价值候选；这是**展示精选**，不是丢弃 ResultSet 数据。

## 5. 结果匹配：标题命中不等于满足需求

搜索之后首先问：**这些结果真的帮助用户完成目标吗？**

典型不匹配：

- 用户要低龄启蒙，结果全是高年级系统课程；
- 用户要可打印练习，结果全是讲解视频；
- 用户要特定教材版本，结果是其他版本；
- 用户要孩子直接使用的材料，结果全是家长方法讨论；
- 用户要实质学习内容，结果是词典、聚合、广告、预览或空壳详情页；
- 用户要具体文件，结果只有介绍页或目录线索。

需求已经清楚时，优先修正搜索角度、来源或 query；不要因为结果差就重新向用户询问已经明确的信息。

只有搜索结果暴露出一个真正未确认的用户分叉，而不同答案会改变下一步时，才回到澄清。

## 6. 候选审查重点

只对准备比较、展示或可能 Inspect 的高潜候选做深入判断。至少考虑：

- **relevance**：是否真的围绕当前主题和目标；
- **usefulness**：拿到它以后能否完成当前任务；
- **target fit**：深度、语言、媒介和使用方式是否适合实际资源对象；
- **constraint fit**：是否满足 must / exclude；
- **substantive**：是否有真实内容，而非空页、聚合、广告、标题党；
- **credibility**：当前任务所需的作者/机构/原始来源证据是否足够；
- **complementarity**：与其他候选相比是否提供不同而有价值的内容/学习体验；
- **evidence level**：当前只是 search metadata，还是已经通过 Inspect 得到更强事实。

允许 `unknown`。unknown 不等于通过，也不等于失败；没有证据不要靠平台名、播放量、标题命中或模型常识补齐。

播放量、收藏量、热度可以作为弱辅助信号，不能替代相关性、适配性和可信度。

明显偏题、违反 must/exclude、纯广告/空壳/明显失效且没有进一步核验价值的候选通常不进入 Presentation。

## 7. 用户背景只用于当前适配判断

候选适配可以使用 OpenClaw 当前上下文中已经可靠提供、且与当前 resource target 明确对应的年龄、年级、基础水平等背景。

但不要：

- 因为候选没有年龄 metadata 就机械删除；
- 把本轮候选特征反向写成长期用户画像；
- 多资源对象之间串用年龄/偏好；
- 在资源 MCP 中新增 Profile 来解决对话上下文问题。

如果几个候选覆盖不同难度但都可能有价值，可以在展示时自然说明差异，而不是为了做一个固定评分先问更多画像字段。

## 8. Inspect 只核验会改变决策的事实

Search 是发现；Inspect 是事实核验。只有某个事实会改变推荐、计数、选择或下载决策时才 Inspect 高潜候选。

典型需要 Inspect：

- 用户明确要求“公开”“无需登录”“可直接阅读/下载”；
- 需要确认资源本体、landing page、metadata 或真实文件格式；
- 标题/摘要不足以判断候选是否有实质内容；
- 某个高潜项是否包含用户要求的关键部分仍不清楚；
- 下载准备需要 fresh Resolution/Representation。

不要为了“流程完整” Inspect 全部候选。

### 公开/无需登录约束

用户明确要求公开、无需登录、可直接阅读或可直接下载时，这是 must constraint。

搜索命中、来源名称或 URL 看起来公开都不能单独证明满足条件。候选只有在当前 Inspect/Resolution 的 availability 事实支持时，才能计入“已满足”的公开可访问候选数量。

`AUTH_REQUIRED`、paywall、blocked、unresolved 不得冒充公开可用。它们可以作为受限备选或当前限制说明，但不能为了凑 N 项进入“满足公开条件”的推荐组。

如果当前主要缺口只是可访问性核验，优先 Inspect 高潜项，而不是继续堆更多同类 Search 结果。

## 9. 下一轮搜索应该关闭具体缺口

好的补搜：

- 已有讲解视频，但用户要可打印练习 → 转文档/worksheet/PDF；
- 已有理论解释，但缺真实过程 → 转视频/纪录片/实验演示；
- 内容相关但可信度不足 → 补官方/专业原始来源；
- 已找到书名但版本不清 → 转图书目录/版本线索；
- 当前只有 landing page，但用户要资源本体 → 围绕本体/表示做 Inspect 或更具体发现；
- 横向比较只覆盖一个来源族，而用户明确要求多来源比较 → 补另一个有不同证据价值的来源族。

差的补搜：

```text
火山科普
火山知识
火山百科
儿童火山知识
```

只替换近义词、加“优质/高赞”或机械增加平台，没有扩大真实搜索空间。

## 10. 什么时候停止

以下情况通常应停止搜索并进入展示/说明：

- 已有足够高质量且互补的候选支持用户做选择；
- 剩余不确定性应通过 Inspect 或用户选择解决，而不是继续 Search；
- 下一轮只能重复同一来源和同一 query 空间；
- 当前来源/平台能力已经明确限制关键条件，继续没有现实改善路线；
- 用户只是“先看看”，当前结果已经足够开始对话式选择；
- 连续补搜没有带来新的有用候选，也没有关闭任何实际缺口。

停止不等于声称“全网没有更好资源”。只表示当前证据足够做下一步，或当前条件下没有明显更好的继续路线。

## 11. 搜索部分失败时保持真实解释

某平台失败、某条 query partial 或当前 ResultSet 为空时：

- 某来源失败不等于资源不存在；
- 不把搜索失败解释成下载/Provider 失败；
- 不因为失败而偷偷换 acquisition route；
- 另一个来源本来就有独立语义价值时，可以按当前目标继续搜索；
- 关键来源/条件无法满足时，向用户说明当前限制。

低相关结果也不证明 Adapter 内部进行了错误分词、截断或改写。只有 Tool 明确返回相应事实时才能这样解释；否则只能说当前 query/来源的召回质量不足。

## 12. ResultSet 与 Presentation 必须区分

ResultSet 是服务端搜索快照，Presentation 是用户**实际看到的有序候选子集**。

流程要求：

1. 先完成候选判断；
2. 在回复中真正向用户展示有序列表；
3. 再用 `resource_presentation_save` 保存与实际展示完全一致的资源和顺序；
4. Presentation 保存成功后，才邀请用户按编号选择。

不要默认展示或保存整个 ResultSet。高度重复、没有额外决策价值的同类内容只保留代表性候选；违反 must/exclude 的项不要为了凑数进入编号列表。

展示内容优先包含：

- 标题；
- 资源类型/来源；
- 为什么匹配当前目标；
- 会影响选择的重要差异；
- 当前限制或尚未核验的信息。

需要给用户原始公开页面时，只使用 Candidate/Resolution 实际返回的 canonical public URL，不从标题或平台名拼接 URL。

如果 Presentation 保存失败，刚才文本列表不能被当成可选择的服务端权威列表；先恢复真实状态，必要时重新展示并保存。

“全部”只表示当前 Presentation 实际可见的全部位置，不包括隐藏 ResultSet 候选、旧 Presentation 或其他轮次结果。

## 13. 不要把自然判断重新变成状态机

内部当然需要判断：

- 现在够不够好；
- 还缺什么；
- 是继续搜、问用户、Inspect 还是展示。

但不要为了表达这些判断再创建新的 `SemanticReview`、`Gap`、`StopDecision` 公共对象、持久状态或固定 JSON。它们只是 Main Agent 的自然推理，不是 MCP 的新事实来源。
