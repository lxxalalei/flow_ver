# Retrieval Guidance

多轮检索的核心不是“多搜几轮”，而是根据真实结果持续修正判断。

## 1. 每一轮只回答四件事

```text
用户真正需要什么
  → 这一轮最值得找什么
  → 真实结果有没有帮助
  → 还缺什么，是否存在明显不同的补搜路线
```

继续之前必须能具体说明“缺口是什么”以及“下一条路线为什么可能补上”。

如果只能说“可能还有更好的”“还有平台没搜”，就停止机械扩散。

## 2. 搜索角度不是关键词变体

例如：

```text
火山科普
火山知识
儿童火山知识
```

基本还是同一搜索空间。

真正不同的角度更像：

```text
喷发原理理解
真实喷发过程观察
可打印实验活动单
```

窄任务一个角度就够；较宽任务优先少量互补方向，不需要凑数量。

## 3. 首轮优先验证方向，而不是追求覆盖率

首轮的价值是验证：

- 当前需求理解是否正确；
- 当前来源职责是否合理；
- query 是否能召回有用内容；
- 用户约束是否真的能满足。

因此不要一开始就铺满所有已知来源，也不要每个平台发多条近义 query。

真实结果能帮助下一轮做更好的选择。

## 4. 结果判断

重点看：

- relevance：是否围绕当前目标；
- usefulness：能不能帮助用户完成目标；
- target fit：深度、语言、媒介是否合适；
- constraint fit：是否满足 must / exclude；
- substantive：是否有真实内容；
- credibility：当前任务所需证据是否足够；
- complementarity：是否与已有候选提供不同价值。

允许 unknown。没有证据不要靠平台名、标题、播放量自动推断质量。

## 5. 什么时候检查具体候选

只有某个未知事实会改变推荐或获取决策时，才对高潜候选进一步 Inspect。

典型情况：

- 版本、创作者或语言不清楚；
- 用户要求公开访问/特定格式；
- 不确定是资源本体还是 landing page；
- 搜索摘要不足以判断。

不要为了“流程完整”检查全部候选。

## 6. 什么时候停止

通常在这些情况下停止继续搜：

- 已有足够高质量且互补的候选；
- 剩余问题应由 Inspect 或用户选择解决；
- 下一轮只能重复同一搜索空间；
- 用户只是先看看，而当前结果已经够用；
- 连续补搜没有带来新的有用内容。

停止表示当前证据足够做下一步，不等于声称“全网没有更好资源”。

## 7. 用户选择基于实际展示内容

候选可以直接在正常对话里展示。

用户说“第 2 个”“这两个”时，只能映射到他实际看到并能合理指代的候选。不要从隐藏结果、未展开页或内部排序中猜用户选择。

真正需要保留的是被选资源的语义身份，例如 URL、平台、标题、作者或稳定平台标识，而不是永久记住某个临时句柄。

## 8. 区分普通推荐与完整枚举

普通推荐搜索关心“找到足够有用的候选”，不需要因为来源还有下一页就全部翻完。

完整枚举任务关心“数据不能漏”，例如：

- 某创作者全部作品；
- 某明确时间范围的完整内容；
- 用户明确要求导出全部列表。

这类任务应使用批量枚举能力直到来源真实结束，再按需分页查看。对话一次只展示 20/50 条不能变成采集上限。

反过来，小规模浏览某个创作者只是预览，不应自动升级成全量采集。

## 9. 平台失败不是语义结论

某个平台搜索失败、认证失败或 partial failure，只说明当前这条能力没有得到结果，不等于“这个资源不存在”。

Agent 应判断：

- 这个来源是否对当前目标仍然关键；
- 是否存在合理的同职责替代来源；
- 是否值得稍后重试；
- 还是当前已有证据已经足够。

不要把技术失败直接翻译成内容结论，也不要为了隐藏失败静默切换到不等价的获取路径。
