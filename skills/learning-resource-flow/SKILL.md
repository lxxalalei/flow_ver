# Learning Resource Research

这个 Skill 的职责不是教模型“怎么调用一套 MCP”，而是让模型在找学习资源时做出更好的语义决策。

核心原则：

> **Agent 负责理解、搜索任务设计与判断；工具负责事实与执行。**

不要把搜索、Inspect、下载、归档组织成固定流水线。根据当前任务只调用真正需要的能力。

## 1. 先还原用户真正要完成什么

不要把用户原话直接改写成关键词。先判断：

- 最终目标是什么：理解、观察、练习、实践、比较、备课、找版本、获取具体文件，还是别的；
- 资源实际给谁使用，已有背景是否会明显改变内容尺度；
- 哪些条件是真正的 must / prefer / exclude；
- 什么样的结果才算“对这个用户有用”。

这些是当前任务的语义，不是要填满的字段。

例如“想让孩子了解火山，形式你定”并不等于搜索“儿童火山优质资料”。更合理的是先想到：需要理解形成与喷发机制，也可能需要直观看到喷发过程；如果用户希望继续自主学习，图文、活动材料或系统课程也可能提供视频没有的价值。

## 2. 只有答案会改变路线时才澄清

提问前先判断：不同答案是否会让我去找明显不同的东西。

应该澄清的典型情况：

- 主题本身过宽，如“历史资料”“科学启蒙”；
- 学段会改变内容尺度，如“物理启蒙”；
- 教材同步资料缺少真正影响内容的版本/册次；
- 多个使用对象背景差异很大，但本次对象不明确；
- 用户给出的硬约束彼此冲突。

不应为了平台、数量、文件格式、完整画像而机械追问。用户已经说“你决定”“都可以”时，应自行做合理探索，不把选择责任再推回用户。

详见 [`references/conversation.md`](references/conversation.md)。

## 3. 先分解需要覆盖的学习价值

搜索角度来自学习价值，不来自关键词变体。

常见价值包括：

- 理解：概念、原理、系统讲解；
- 观察：真实过程、动画、纪录片、实验现象；
- 练习：题卡、习题、worksheet、可打印任务；
- 实践：实验、手工、项目、活动方案；
- 沉浸：故事、朗读、人物叙事；
- 比较：方法、版本、观点、原始证据；
- 获取：明确书名、版本、ISBN、文件、详情页。

“火山科普 / 火山知识 / 儿童火山知识”仍然是同一搜索空间；“喷发原理理解 / 真实喷发过程观察 / 可打印实验单”才是不同价值路线。

路线数量不是目标。窄任务可能只有一条；开放式或复合任务可能需要多条。不要为了少调用工具而提前压缩掉仍有明显价值差异的路线，也不要为了显得全面凑固定数量。

## 4. 派发前设计搜索任务

在真正搜索前，至少要能在内部回答：

1. 这一条搜索任务要补哪个用户价值或事实缺口？
2. 需要什么内容形态或证据？
3. 哪类来源最适合承担这项职责？
4. 在这个来源里，人会怎么搜？
5. 它和其他已计划路线有什么不同？

这是即时的语义规划，不需要创建 Plan、Task DTO 或任何持久对象。

例如：

```text
用户目标：让孩子理解火山并能直观看到喷发

任务 A：形成/喷发机制
需要：可靠、结构化解释
来源：专业/官方 Web
query：火山形成 喷发原理 科普

任务 B：过程观察
需要：动画或真实过程
来源：视频生态
query：火山喷发 原理 动画 实验演示
```

如果还需要可复用学习材料，可以再形成独立的图文/活动单路线。关键是职责不同，不是平台数量多。

## 5. 来源选择要有职责

来源不是覆盖清单。每个进入搜索计划的来源都应该回答：**它能提供当前其他路线没有的什么价值？**

例如：

- 需要看到过程 → 视频生态；
- 同步课程/教材体系 → 结构化教育来源；
- 朗读/听书/路上听 → 音频来源；
- 方法比较 → 问答、专业文章；
- 高可信解释 → 官方/专业来源；
- 书名、版本、ISBN → 图书目录/图书来源；
- 课件、讲义、练习 → 文档来源。

### Host Web Search 是通用发现层

普通 Web Search 不只是“专门平台都失败后的 fallback”。它可以跨生态发现官方机构、专业文章、博物馆/出版社页面、教程、PDF/文档以及未单独接入的长尾资源。

**开放式任务的首轮默认包含一条 Host Web Search 路线。**任务没有明确限定单一平台或单一形态时都算开放式；下列情况是典型获益场景：

- 用户说形式不限、来源不限；
- 目标需要官方/专业解释或原始材料；
- 可能存在有价值的图文、文档、地图、活动材料或长尾网页；
- 没有单一专门生态天然覆盖主要需求。

只有两类情况跳过：用户明确只要某平台或某形态；或任务窄到单一价值路线已被专门平台完全覆盖。跳过时心里能说出理由即可，不需要向用户解释。

选中具体网页后，再把具体 URL 交给资源能力进入后续检查或获取。不要因为 MCP 注册了某个平台就机械搜索它。

具体来源生态见 [`references/source-routing.md`](references/source-routing.md)。

## 6. Query 要像人在对应来源里真实搜索

Query 应体现“主题 + 当前切面”，只加入真正影响召回的条件。

不要用“优质、精品、高赞、权威、适合孩子”等评价词代替后续判断；这些通常不能提高召回质量。

同一个目标在不同职责的来源里 query 可以不同。例如：

```text
专业解释：火山形成 喷发原理 科普
视频观察：火山喷发 原理 动画 实验演示
活动材料：火山 实验 活动单 小学生
```

首轮优先少量、聚焦的 query，但“少量”不能成为漏掉主要价值路线的理由。真实结果回来后再调整任务和 query。

## 7. 判断“有用”，不是判断“有结果”

对准备推荐的候选重点判断：

- relevance：是否真的围绕当前目标；
- usefulness：能否帮助用户完成目标；
- target fit：深度、语言、媒介是否适合实际使用者；
- constraint fit：是否满足 must / exclude；
- substantive：是否有实质内容，而不是聚合页、广告或空壳；
- credibility：当前任务所需可信度是否足够；
- complementarity：是否和已有候选提供不同价值。

允许“不确定”。没有证据时不要根据标题、平台名、播放量自动补齐事实。

## 8. Gap 不只看内容缺失，也看覆盖盲区

继续搜索前至少判断两类 Gap：

### 内容 Gap

- 用户要理解机制，但只有题目解析；
- 用户要可打印材料，但只有视频；
- 用户要版本信息，但只有泛化介绍。

### Coverage Gap

如果用户没有限定媒介/来源，而当前高潜候选几乎全部来自同一种资源形态或同一种来源生态，应进一步判断：**另一种形态或来源是否能为用户目标增加明显价值？**

如果能，这种集中本身就是值得补搜的覆盖盲区。例如开放式“火山学习资料”只有 B 站视频时，专业图文、官方科普或活动材料可能仍有独特价值。

但不要机械追求多样性：用户明确只要真实视频时，全是视频不是 Gap；用户明确要教材同步课时，结构化教育来源集中也完全合理。

补搜前必须能具体回答：

1. 现在缺什么价值或覆盖？
2. 下一条路线为什么有机会补上？

“还有平台没搜”“可能还有更好的”都不是充分理由。

## 9. 停止条件看目标覆盖，不看候选数量

通常同时满足这些条件时才适合停止：

- 用户目标中的主要价值已经被足够好的候选覆盖；
- must / exclude 没有明显未满足项；
- 当前候选没有仍然重要的内容 Gap；
- 如果任务是开放式的，也没有明显且有价值的单一生态/单一形态盲区；
- 下一轮只能重复已有搜索空间，或连续补搜没有带来新的有用内容。

几个看起来不错的视频不自动等于开放式资源研究已经完成；几十个同质结果也不等于覆盖充分。

停止不代表声称“全网没有更好资源”，只代表当前证据已经足够进入下一步。

详见 [`references/retrieval.md`](references/retrieval.md)。

## 10. Inspect 是为决策补事实，不是固定步骤

只有某个未知事实会改变推荐、选择或获取决策时，才检查高潜候选，例如：

- 是否真的是目标资源本体而非 landing page；
- 版本/创作者/语言等关键事实不清楚；
- 用户明确要求公开访问、特定格式或可获取性；
- 搜索摘要不足以判断。

不要为了“流程完整”把所有候选都 Inspect。

详见 [`references/inspection.md`](references/inspection.md)。

## 11. 区分预览、完整枚举和研究搜索

用户只是“看看这个创作者有哪些作品”时，可以小规模浏览并判断。

用户明确要求“这个创作者全部作品”“某时间段完整结果”等完整枚举时，这是**数据完整性任务**，不是普通推荐搜索：应使用批量能力直到来源真实结束，并分页读取结果。聊天里一次展示多少条不能变成采集上限。

合集、系列、专辑、教材等是**内容容器**，不是创作者。用户要求“这个合集全部视频”“这个专辑全部音频”“这本教材全部课程”时，同样属于完整枚举，但应展开该容器本身，而不是把容器 URL 当成 creator。展开得到的每个子资源仍只是候选，后续下载仍以用户实际选择为前提。

反过来，普通研究任务不因为来源还存在更多页就自动全量翻完；是否继续仍由目标覆盖和 Gap 决定。

## 12. 用户选择是语义，不是永久句柄

用户说“第 2 个”“这两个”“刚才那个作者的视频”时，Agent 要理解他真正选中了哪个资源。

应该保留的是当前对话里的资源语义：URL、平台、标题、作者、稳定平台标识等，而不是把某个临时 `resource_id` 当成永久身份。

只能把用户实际看到或明确指代的资源解释为选择；不要从隐藏候选或未展示的批量结果里猜编号。

如果 MCP 重启导致临时句柄失效，不要重新执行整套研究任务。优先根据已经选中的 URL 或稳定标识重新定位同一个资源；只有无法确认原资源时，才重新进入发现阶段。

## 13. 下载与归档的语义边界

下载是副作用。只有用户已经明确表达“下载、保存、获取下来”等意图时才执行；如果意图和对象已经明确，不要再制造一轮形式化确认。

下载成功与否只依据真实工具结果，不能因为“已经开始”或“理论上可下载”就说成功。

下载完成后，若用户没有明确要求只做临时获取，可将真实文件整理进资料库。分类由 Agent 根据资源内容判断；无法可靠分类时进入待分类，而不是为了填满分类强行猜测或额外追问。

详见 [`references/acquisition.md`](references/acquisition.md) 与 [`references/archive.md`](references/archive.md)。

## 14. 与 MCP 的边界

`education-resources` MCP 是数据面和执行能力，不是这个 Skill 的业务模型。

Skill 可以决定：

- 用户真正要解决什么；
- 应设计哪些互补搜索任务；
- 哪些来源职责值得派发；
- 首轮 Web Search 路线是否已包含（或明确知道为何跳过）；
- 候选是否真正有用；
- 是否存在内容 Gap 或 Coverage Gap；
- 什么时候继续、什么时候停止；
- 用户是否已经选定具体资源；
- 用户是否已经表达获取意图；
- 下载后资源应如何语义分类。

Skill 不复制：

- Tool 参数说明、返回字段说明；
- Provider/Adapter 内部实现；
- Job 文件结构；
- MCP 的平台 Registry；
- Flow / ResultSet / Presentation / Selection / Plan / digest 等后端状态模型。

具体 Tool 形状与当前能力始终以运行时 MCP schema 和真实返回为准。不要为了恢复内部状态去读项目源码，也不要猜不存在的接口。

## 15. 面向用户的结果

用户最终需要的是资源和判断，不是内部研究术语。

通常只展示：

- 必要的自然澄清；
- 当前重点搜索方向（只有说明它确实有帮助时）；
- 少量真正值得选择的候选及差异；
- 仍未确认的重要事实；
- 用户要求获取后，真实下载/归档结果。

不要把内部 Search intent、Dispatch、Coverage Gap 变成要求用户理解的流程对象。
