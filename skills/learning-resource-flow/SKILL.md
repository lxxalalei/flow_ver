# Learning Resource Research

这个 Skill 的职责不是教模型“怎么调用一套 MCP”，而是让模型在找学习资源时做出更好的语义决策。

核心原则：

> **Agent 负责理解与判断；工具负责事实与执行。**

不要把搜索、Inspect、下载、归档组织成固定流水线。根据当前任务只调用真正需要的能力。

## 1. 先还原用户真正要完成什么

不要把用户原话直接改写成关键词。先判断：

- 最终目标是什么：理解、观察、练习、实践、比较、备课、找版本、获取具体文件，还是别的；
- 资源实际给谁使用，已有背景是否会明显改变内容尺度；
- 哪些条件是真正的 must / prefer / exclude；
- 什么样的结果才算“对这个用户有用”。

这些是当前任务的语义，不是要填满的字段。

例如“想让孩子了解火山，形式你定”并不等于搜索“儿童火山优质资料”。更合理的是先想到：孩子需要理解喷发原理，也可能需要直观看到喷发过程，然后再决定来源。

## 2. 只有答案会改变路线时才澄清

提问前先判断：不同答案是否会让我去找明显不同的东西。

应该澄清的典型情况：

- 主题本身过宽，如“历史资料”“科学启蒙”；
- 学段会改变内容尺度，如“物理启蒙”；
- 教材同步资料缺少真正影响内容的版本/册次；
- 多个使用对象背景差异很大，但本次对象不明确；
- 用户给出的硬约束彼此冲突。

不应为了平台、数量、文件格式、完整画像而机械追问。用户已经说“你决定”“都可以”时，应自行做合理探索，不把选择责任再推回用户。

详见 [`references/conversation.md`](references/conversation.md)。

## 3. 搜索角度来自学习价值，不来自关键词变体

先想用户要获得什么价值，再想去哪搜。

常见价值角度包括：

- 理解：概念、原理、系统讲解；
- 观察：真实过程、动画、纪录片、实验现象；
- 练习：题卡、习题、worksheet、可打印任务；
- 实践：实验、手工、项目、活动方案；
- 沉浸：故事、朗读、人物叙事；
- 比较：方法、版本、观点、原始证据；
- 获取：明确书名、版本、ISBN、文件、详情页。

“火山科普 / 火山知识 / 儿童火山知识”仍然是同一搜索空间；“喷发原理理解 / 真实喷发过程观察 / 可打印实验单”才是不同方向。

窄任务一个方向就够；较宽任务通常只需要 1–3 个真正互补的方向，不要为了显得全面而扩散。

## 4. 来源选择要有职责

来源不是覆盖清单。每个进入搜索计划的来源都应该回答：**它能提供当前其他来源没有的什么价值？**

例如：

- 需要看到过程 → 视频生态；
- 同步课程/教材体系 → 结构化教育来源；
- 朗读/听书/路上听 → 音频来源；
- 方法比较 → 问答、专业文章；
- 高可信解释 → 官方/专业来源；
- 书名、版本、ISBN → 图书目录/图书来源；
- 课件、讲义、练习 → 文档来源。

普通网页发现优先使用宿主 Web Search；选中具体网页后再交给资源 MCP 进入后续获取能力。不要因为 MCP 注册了某个平台就机械搜索它。

具体来源生态见 [`references/source-routing.md`](references/source-routing.md)。

## 5. Query 要像人在对应来源里真实搜索

Query 应体现“主题 + 当前切面”，只加入真正影响召回的条件。

不要用“优质、精品、高赞、权威、适合孩子”等评价词代替后续判断；这些通常不能提高召回质量。

同一个方向在不同来源中的 query 可以不同，因为来源职责不同。例如：

```text
原理解释：火山形成 喷发原理 科普
过程观察：火山喷发 原理 动画 实验演示
```

首轮优先少量、聚焦的 query。真实结果出来后再决定是否需要下一轮。

## 6. 判断“有用”，不是判断“有结果”

对准备推荐的候选重点判断：

- relevance：是否真的围绕当前目标；
- usefulness：能否帮助用户完成目标；
- target fit：深度、语言、媒介是否适合实际使用者；
- constraint fit：是否满足 must / exclude；
- substantive：是否有实质内容，而不是聚合页、广告或空壳；
- credibility：当前任务所需可信度是否足够；
- complementarity：是否和已有候选提供不同价值。

允许“不确定”。没有证据时不要根据标题、平台名、播放量自动补齐事实。

## 7. 补搜必须由具体 Gap 驱动

继续搜索前必须能具体回答两个问题：

1. 现在还缺什么？
2. 下一条路线为什么有机会补上？

如果只能说“也许还有更好的”“还有平台没搜”，就不应继续机械扩散。

通常在这些情况下停止：

- 已有足够高质量且互补的候选；
- 剩余问题应该通过检查具体候选或让用户选择解决；
- 下一轮只能重复同一搜索空间；
- 连续补搜没有带来新的有用内容。

停止不代表声称“全网没有更好资源”，只代表当前证据已经足够进入下一步。

详见 [`references/retrieval.md`](references/retrieval.md)。

## 8. Inspect 是为决策补事实，不是固定步骤

只有某个未知事实会改变推荐、选择或获取决策时，才检查高潜候选，例如：

- 是否真的是目标资源本体而非 landing page；
- 版本/创作者/语言等关键事实不清楚；
- 用户明确要求公开访问、特定格式或可获取性；
- 搜索摘要不足以判断。

不要为了“流程完整”把所有候选都 Inspect。

详见 [`references/inspection.md`](references/inspection.md)。

## 9. 区分预览、完整枚举和研究搜索

用户只是“看看这个创作者有哪些作品”时，可以小规模浏览并判断。

用户明确要求“这个创作者全部作品”“某时间段完整结果”等完整枚举时，这是**数据完整性任务**，不是普通推荐搜索：应使用批量能力直到来源真实结束，并分页读取结果。聊天里一次展示多少条不能变成采集上限。

反过来，普通研究任务不因为来源还存在更多页就自动全量翻完；是否继续仍由用户目标和 Gap 决定。

## 10. 用户选择是语义，不是永久句柄

用户说“第 2 个”“这两个”“刚才那个作者的视频”时，Agent 要理解他真正选中了哪个资源。

应该保留的是当前对话里的资源语义：URL、平台、标题、作者、稳定平台标识等，而不是把某个临时 `resource_id` 当成永久身份。

只能把用户实际看到或明确指代的资源解释为选择；不要从隐藏候选或未展示的批量结果里猜编号。

如果 MCP 重启导致临时句柄失效，不要重新执行整套研究任务。优先根据已经选中的 URL 或稳定标识重新定位同一个资源；只有无法确认原资源时，才重新进入发现阶段。

## 11. 下载与归档的语义边界

下载是副作用。只有用户已经明确表达“下载、保存、获取下来”等意图时才执行；如果意图和对象已经明确，不要再制造一轮形式化确认。

下载成功与否只依据真实工具结果，不能因为“已经开始”或“理论上可下载”就说成功。

下载完成后，若用户没有明确要求只做临时获取，可将真实文件整理进资料库。分类由 Agent 根据资源内容判断；无法可靠分类时进入待分类，而不是为了填满分类强行猜测或额外追问。

详见 [`references/acquisition.md`](references/acquisition.md) 与 [`references/archive.md`](references/archive.md)。

## 12. 与 MCP 的边界

`education-resources` MCP 是数据面和执行能力，不是这个 Skill 的业务模型。

Skill 可以决定：

- 什么时候搜索、搜什么；
- 什么时候需要检查事实；
- 用户是否已经选定具体资源；
- 是否存在继续搜索的真实缺口；
- 用户是否已经表达获取意图；
- 下载后资源应如何语义分类。

Skill 不复制：

- Tool 参数说明、返回字段说明；
- Provider/Adapter 内部实现；
- Job 文件结构；
- MCP 的平台 Registry；
- Flow / ResultSet / Presentation / Selection / Plan / digest 等后端状态模型。

具体 Tool 形状与当前能力始终以运行时 MCP schema 和真实返回为准。不要为了恢复内部状态去读项目源码，也不要猜不存在的接口。

## 13. 面向用户的结果

用户最终需要的是资源和判断，不是内部研究术语。

通常只展示：

- 必要的自然澄清；
- 当前重点搜索方向（只有说明它确实有帮助时）；
- 少量真正值得选择的候选及差异；
- 仍未确认的重要事实；
- 用户要求获取后，真实下载/归档结果。

不要要求用户理解 MCP、Provider、Representation、Job 内部文件或任何已经废弃的工作流对象。
