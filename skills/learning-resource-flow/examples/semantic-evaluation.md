# Semantic Evaluation Guide

这份评测用于判断 `learning-resource-flow` 是否真的提升了模型找资源的语义能力，而不是判断它有没有按固定工具流程走完。

## 1. 主要评什么

同一个用户输入、同一个 Main Agent、同一组可用资源能力下，重点比较：

1. **Need reconstruction**：是否还原用户最终想解决的问题，而不是直接复制关键词；
2. **Clarification judgment**：该问关键分叉时是否问，不该问时是否直接行动；
3. **Search angle quality**：是否形成真正不同的学习价值路线；
4. **Dispatch design**：是否把价值路线转成职责清楚、互补的搜索任务，而不是直接挑一个最顺手的平台；
5. **Source routing**：来源是否因为当前内容/证据需求被选择，Host Web Search 是否在开放式任务中被合理考虑；
6. **Query quality**：query 是否像人在对应来源里真实搜索；
7. **Result judgment**：是否能识别“关键词命中但实际没用”；
8. **Coverage judgment**：是否识别内容 Gap、单一媒介/单一生态的有价值覆盖盲区，同时避免机械追求多样性；
9. **Gap / stop judgment**：是否能指出具体缺口，并据此决定补搜或停止；
10. **Action boundary**：是否正确理解用户选择、下载意图和完整枚举要求。

工具调用数量只是成本指标，不是质量本身。少调用但漏掉主要价值路线，不比多一次有意义搜索更好。

## 2. Action boundary 是底线，不是主得分

语义做得再好，也不能破坏这些基本边界：

- 不把用户没看到、没指代的隐藏候选解释成选择；
- 用户明确说“先别下载”时不执行下载；
- 用户已经明确要求下载且对象清楚时，不制造形式化二次确认；
- 没有真实文件时不说下载成功；
- 技术失败不等于内容不存在；
- 完整枚举任务不能因为单页展示数量而截断数据；
- 临时资源句柄失效时，优先重新定位已经选中的同一资源，而不是重做整个研究任务。

这些只是保证 Agent 没做错事，不能证明最终资源质量高。

## 3. A/B 方法

建议用同一个模型、同一个资源环境、同一输入比较不同 Skill 版本。

每个 case 记录：

- 是否澄清以及澄清了什么；
- 用户目标被分成了哪些学习价值；
- 实际设计了哪些搜索任务，每条任务负责什么；
- 实际选择了哪些来源和 query；
- 开放式任务中是否合理使用或考虑了 Host Web Search；
- 第一轮候选是否真正有用；
- 候选是否过度集中在一种媒介/生态，以及这种集中是否真的构成 Gap；
- 是否识别结果方向错误；
- 是否形成具体内容 Gap 或 Coverage Gap；
- 是否进行了有意义的补搜；
- 是否知道什么时候停止；
- 用户最终看到的候选是否更匹配目标；
- 是否正确处理用户选择、下载意图和完整枚举；
- Tool 调用数量和无效搜索次数。

不要用“调用更少”直接判定更好，也不要用“流程走得完整”代替语义质量。

## 4. 建议评分

每个语义维度使用 0/1/2 三档即可：

- `0`：核心方向错误、明显漏掉主要价值路线，或完全机械；
- `1`：基本相关，但搜索任务设计单薄、覆盖判断不足或仍有无效扩散；
- `2`：目标还原合理，派发任务职责清楚，来源与 query 有依据，并能根据真实结果调整覆盖和停止。

不要把这些维度加权成看似精确的总分。更重要的是观察新版是否在多数真实任务上稳定更好，以及有没有新的系统性退化。

## 5. 重点失败模式

- 用户原话直接变 query；
- 需求开放却直接挑最顺手的平台开始搜，没有形成搜索任务设计；
- 形式不限却只得到几个同平台视频就停止；
- 开放式资源发现长期完全不考虑 Host Web Search；
- 把“已有几个好结果”误当成“主要价值已经覆盖”；
- 为了平台覆盖率搜一圈所有来源；
- 为了形式多样强行凑视频、图文、音频、PDF；
- 每个平台生成多条近义 query；
- 结果数量多就认为“够好了”；
- 没有具体 Gap 仍继续补搜；
- 有明显 Coverage Gap 却因为已有候选而过早停止；
- 用户已经限定视频/同步课等形态，却仍为了多样性搜索无关来源；
- 搜索失败后反过来追问用户已经明确的信息；
- 把探索用的载体/来源写成用户长期偏好；
- 为普通任务自动上多 Agent；
- 只看标题、平台名、播放量，不判断实际对象适配；
- 把预览数量当成完整枚举上限；
- 用户明确下载后仍追加无意义的确认；
- 临时句柄丢失后重新跑整套研究，导致资源对象漂移。

## 6. 静态 case 与真实 OpenClaw 验证

静态回归 case 只能证明 Skill 文本覆盖了某些决策边界，不能证明真实对话质量。

里程碑验收仍应抽取代表性 case 在 OpenClaw 中真实执行，保存：

- 用户输入；
- 关键澄清；
- 搜索价值分解；
- 实际 Dispatch 与 query；
- 真实候选；
- Coverage / Gap / 停止判断；
- 用户可见回复；
- 如果涉及获取，真实下载/归档结果。

后端单测或 MCP 直调不能替代这一层语义验收。尤其要关注：新版是否真的从“几个视频就停”改善为“覆盖主要价值后再停”，而不是简单增加工具调用次数。
