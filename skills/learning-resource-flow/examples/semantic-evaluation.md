# Semantic Evaluation Guide

这份评测用于判断 `learning-resource-flow` 是否真的提升了模型找资源的语义能力，而不是判断它有没有按固定工具流程走完。

## 1. 主要评什么

同一个用户输入、同一个 Main Agent、同一组可用资源能力下，重点比较：

1. **Need reconstruction**：是否还原用户最终想解决的问题，而不是直接复制关键词；
2. **Clarification judgment**：该问关键分叉时是否问，不该问时是否直接行动；
3. **Search angle quality**：是否形成少量真正互补的学习价值方向；
4. **Source routing**：来源是否因为当前内容/证据需求被选择；
5. **Query quality**：query 是否像人在对应来源里真实搜索；
6. **Result judgment**：是否能识别“关键词命中但实际没用”；
7. **Gap judgment**：是否能指出具体缺口，并据此决定补搜或停止；
8. **Action boundary**：是否正确理解用户选择、下载意图和完整枚举要求。

工具调用数量只是成本指标，不是质量本身。

## 2. Action boundary 是底线，不是主得分

语义做得再好，也不能破坏这些基本边界：

- 不把用户没看到、没指代的隐藏候选解释成选择；
- 用户明确说“先别下载”时不执行下载；
- 用户已经明确要求下载且对象清楚时，不制造形式化二次确认；
- 没有真实文件时不说下载成功；
- 技术失败不等于内容不存在；
- 完整枚举任务不能因为单页展示数量而截断数据；
- 临时资源句柄失效时，优先重新定位已经选中的同一资源，而不是重做整个研究任务。

这些只是保证 Agent 没做错事，不能证明最终资源质量高。

## 3. A/B 方法

建议用同一个模型、同一个资源环境、同一输入比较不同 Skill 版本。

每个 case 记录：

- 是否澄清以及澄清了什么；
- 形成了哪些搜索角度；
- 实际选择了哪些来源和 query；
- 第一轮候选是否真正有用；
- 是否识别结果方向错误；
- 是否形成具体 Gap；
- 是否进行了有意义的补搜；
- 是否知道什么时候停止；
- 用户最终看到的候选是否更匹配目标；
- 是否正确处理用户选择、下载意图和完整枚举；
- Tool 调用数量和无效搜索次数。

不要用“调用更少”直接判定更好，也不要用“流程走得完整”代替语义质量。

## 4. 建议评分

每个语义维度使用 0/1/2 三档即可：

- `0`：核心方向错误，或完全机械；
- `1`：基本相关，但仍有明显模板化/无效扩散；
- `2`：目标还原合理，来源与 query 有明确职责，并能根据真实结果调整。

不要把这些维度加权成看似精确的总分。更重要的是观察新版是否在多数真实任务上稳定更好，以及有没有新的系统性退化。

## 5. 重点失败模式

- 用户原话直接变 query；
- 为了平台覆盖率搜一圈所有来源；
- 每个平台生成多条近义 query；
- 结果数量多就认为“够好了”；
- 没有具体 Gap 仍继续补搜；
- 搜索失败后反过来追问用户已经明确的信息；
- 把探索用的载体/来源写成用户长期偏好；
- 为普通任务自动上多 Agent；
- 只看标题、平台名、播放量，不判断实际对象适配；
- 把预览数量当成完整枚举上限；
- 用户明确下载后仍追加无意义的确认；
- 临时句柄丢失后重新跑整套研究，导致资源对象漂移。

## 6. 静态 case 与真实 OpenClaw 验证

静态回归 case 只能证明 Skill 文本覆盖了某些决策边界，不能证明真实对话质量。

里程碑验收仍应抽取代表性 case 在 OpenClaw 中真实执行，保存：

- 用户输入；
- 关键澄清；
- 搜索方向和 query；
- 真实候选；
- Gap/停止判断；
- 用户可见回复；
- 如果涉及获取，真实下载/归档结果。

后端单测或 MCP 直调不能替代这一层语义验收。
