# Retrieval Guidance

多轮检索的核心不是“尽量少搜”或“多搜几轮”，而是让每次搜索都增加对用户目标有价值的新证据。

## 1. 每轮先看任务设计，再看结果

```text
用户真正需要什么
  → 哪些学习价值还需要覆盖
  → 为每个价值设计什么搜索任务
  → 真实结果有没有帮助
  → 还缺什么内容或覆盖
  → 是否存在明显不同的补搜路线
```

搜索任务可以只是 Agent 当前思考中的临时结构，不需要创建持久 Plan 或工作流对象。

## 2. 搜索角度不是关键词变体

例如：

```text
火山科普
火山知识
儿童火山知识
```

基本还是同一搜索空间。

真正不同的价值路线更像：

```text
喷发原理理解
真实喷发过程观察
可打印实验活动单
```

路线数量由任务决定。窄任务一条可能足够；开放式或复合任务可以有多条。不要因为“少调用工具”而把明显不同的价值路线合并掉，也不要为了覆盖平台数量硬拆任务。

## 3. 首轮目标是获得足够信息增益，不是最小调用次数

首轮应该帮助验证：

- 当前需求理解是否正确；
- 主要价值路线是否合理；
- 哪些来源对这些价值有直接匹配；
- query 是否能召回有用内容；
- 用户约束是否真的能满足。

如果任务开放、形式不限，多个对当前价值有直接匹配的来源可以并行或连续参与召回；它们不必拥有互斥职责。

例如“让孩子了解火山，形式不限”可以同时验证：

- OpenClaw `web_search` 是否能发现专业/官方的机制解释、图文或长尾材料；
- Bilibili 是否有动画、中长讲解或实验演示；
- Douyin 是否有有效的短科普或短演示；
- 如果真实影像/纪录片对目标有价值，CCTV 是否能补这一类候选。

这不是为了平台覆盖率，也不是要求每个平台承担唯一职责，而是让合理来源的真实候选参与竞争。

同时不要因为“平台可能有”就全平台扫描。SmartEdu 只有在教材、同步、课时等课程信号出现时才具有直接匹配；“用户是学生”本身不够。

## 4. OpenClaw `web_search` 是跨生态发现能力

Host Web Search 在运行时就是 OpenClaw 原生 `web_search`。它与 MCP 的 `resource_search` 是并列召回能力，不是 fallback 关系，也不需要在 MCP 内再实现一遍。

它适合跨站发现：

- 官方和专业机构页面；
- 博物馆、出版社、教育机构等长尾来源；
- 专业文章、教程、地图；
- PDF/PPT/worksheet 等文档；
- 未单独接入 MCP 的网页资源。

开放式资源研究、形式/来源不限、没有专门平台天然覆盖主要目标的任务，首轮默认包含 `web_search` 路线。

反过来，用户明确只要某个平台，或已经给出具体 URL 且当前只是获取/转换这个 URL 时，不需要先 `web_search`。窄任务若专门生态已经直接覆盖主要目标，也可以跳过 Web；跳过时只需要有明确语义理由。

### Web 命中不要批量导入 MCP

`web_search` 的结果先作为普通候选参与 Evidence 判断。搜索结果能够支持什么，就只判断到什么：标题、URL、来源域名、摘要/片段、日期等不能自动升级成页面全文事实。

不要把每一个搜索命中都 `resource_import_url`。只有以下情况才让具体 URL 进入 MCP：

- 用户已经选中它并明确要求保存、下载、归档或转换；
- 页面本体存在一个会改变推荐/获取决策的关键未知事实；
- 后续需要 MCP 的 Inspect / Download / HTML Design / Archive 能力。

如果用户只是要“找几篇值得看的资料”，搜索证据已经足够判断的 Recommendable Web 候选可以直接推荐，不需要先变成 MCP Resource。

### Web 与 MCP 候选要语义去重

如果 `web_search` 和某个平台的 `resource_search` 命中了同一个实际资源，不要因为来自两个工具就向用户展示两次。

用当前可见的 URL、平台稳定标识、标题、作者等证据判断是否同一资源；同一资源只保留一个语义候选，并综合更丰富的证据。这里不需要持久跨工具 ID，也不需要后端 canonical/projection。

## 5. 结果判断

重点看：

- relevance：是否围绕当前目标；
- usefulness：能不能帮助用户完成目标；
- target fit：深度、语言、媒介是否合适；
- constraint fit：是否满足 must / exclude；
- substantive：是否有真实内容；
- credibility：当前任务所需证据是否足够；
- complementarity：是否与已有候选提供不同价值。

允许 unknown。没有证据不要靠平台名、标题、播放量自动推断质量。平台在 routing 阶段的“典型优势”也不能替具体候选加分。

对 Web Search 尤其要区分 snippet 和页面本体：搜索摘要只能证明摘要真实显示的内容，不能据此声称完整页面结构、全文结论、文件格式或可下载性。

## 6. 两类 Gap

### 内容 Gap

当前候选没有覆盖用户明确需要的内容或用途。

例如：

- 用户要“看懂过程”，只有背诵知识点；
- 用户要练习，只有讲解；
- 用户要可打印，只有视频；
- 用户要版本事实，只有泛化介绍。

### Coverage Gap

当前单条候选可能不错，但整个候选集存在明显覆盖盲区。

如果用户没有限定媒介/来源，而高潜候选几乎全部集中在一种资源形态或一个来源生态，先问：

> 是否存在另一种形态/来源，能为用户目标补上当前候选明显缺少的价值？

如果有，这就是 Coverage Gap。

例如开放式火山学习资料目前只有短视频时，短视频可能已经很好地完成“直观认识”，但专业图文或更完整讲解可能仍然缺失。

“来源单一”本身不是罪。用户明确只要视频时，全是视频完全正常；同步教材任务高度集中于教育平台也可能最合理。

## 7. 补搜必须能说明新增价值

继续之前必须能具体回答：

1. 现在缺什么？
2. 是内容缺口还是覆盖盲区？
3. 下一条路线为什么可能补上？
4. 新路线与已经搜索过的空间有什么实质差别？

如果只能说：

- “可能还有更好的”；
- “还有平台没搜”；
- “再多找几个保险”；

就不应继续机械扩散。

**未搜索的平台本身不是 Gap。**即使某个平台属于 eligible source，也只有当前结果暴露了它可能补的具体价值时，才需要在后续补搜。

同样，`web_search` 已经搜过也不是继续 Web 搜索的充分理由；只有新的 query 能进入实质不同的搜索空间、补明确 Gap，才值得下一轮。

但如果只是因为已有 3～5 个不错候选就停止，也是不充分的。候选数量不能替代目标覆盖判断。

## 8. 来源集中与媒介集中检查

开放式任务在准备停止前，快速检查当前高潜候选的结构：

- 是否全部是同一种视频形态？
- 是否全部来自同一个社交平台？
- 是否只有经验内容，没有专业/原始材料？
- 是否只有讲解，没有用户需要的练习/实践/可打印材料？
- 是否只有目录线索，没有资源本体？

只有当另一条路线确实能补明显价值时才补搜。不要为了“视频 + 图文 + 音频 + PDF”形式齐全而凑类型，也不要为了“还有一个合理平台没搜”继续。

## 9. 什么时候检查具体候选

只有某个未知事实会改变推荐或获取决策时，才对高潜候选进一步 Inspect。

典型情况：

- 版本、创作者或语言不清楚；
- 用户要求公开访问/特定格式；
- 不确定是资源本体还是 landing page；
- 搜索摘要不足以判断。

对于 `web_search` 命中的 URL，先判断这个未知是否真的会改变决策；只有高潜候选需要页面本体事实时才 Import/Inspect，不要把 Import 当成 Web Search 的固定后处理。

不要为了“流程完整”检查全部候选。

## 10. 什么时候停止

停止依据是**目标覆盖已经足够**，不是“已经搜过一个平台”“所有 eligible source 都搜过”或“已经有几个结果”。

通常需要满足：

- 主要学习价值已经有足够好的候选；
- must / exclude 没有明显未满足项；
- 没有仍然重要的内容 Gap；
- 开放式任务没有明显且值得补的单一生态/单一形态盲区；
- 已经没有一条能明确说明“下一轮会新增什么价值”的高信息增益路线；
- 用户明确表示当前这些已经够了。

停止不等于声称“全网没有更好的”，只是当前证据足以进入选择或使用阶段。

## 11. 用户选择基于实际展示内容

候选可以直接在正常对话里展示。

用户说“第 2 个”“这两个”时，只能映射到他实际看到并能合理指代的候选。不要从隐藏结果、未展开页或内部排序中猜用户选择。

真正需要保留的是被选资源的语义身份，例如 URL、平台、标题、作者或稳定平台标识，而不是永久记住某个临时句柄。

Web 候选尤其以 URL 为主要稳定身份。用户随后说“把刚才第 2 篇保存下来”时，应复用已经展示并选中的 URL，直接进入 `resource_import_url`；不要重新 Web Search 去猜同一篇，也不要要求它先拥有 MCP `resource_id` 才能被选择。

## 12. 区分普通推荐与完整枚举

普通推荐搜索关心“找到足够有用且覆盖目标的候选”，不需要因为来源还有下一页就全部翻完。

完整枚举任务关心“数据不能漏”，例如：

- 某创作者全部作品；
- 某明确时间范围的完整内容；
- 用户明确要求导出全部列表。

这类任务应使用批量枚举能力直到来源真实结束，再按需分页查看。对话一次只展示 20/50 条不能变成采集上限。

反过来，小规模浏览某个创作者只是预览，不应自动升级成全量采集。

`web_search` 的普通结果页也不是完整枚举工具。用户要求某个已知容器/创作者“全部”时，应使用对应结构化 Expand/枚举能力，而不是反复 Web Search 猜完整列表。

## 13. 平台失败不是语义结论

某个平台搜索失败、认证失败或 partial failure，只说明当前这条能力没有得到结果，不等于“这个资源不存在”。

Agent 应判断：

- 这个来源是否对当前目标仍然关键；
- 是否存在合理的同职责或同价值替代来源；
- 是否值得稍后重试；
- 还是当前已有证据已经足够。

不要把技术失败直接翻译成内容结论，也不要为了隐藏失败静默切换到不等价的获取路径。
