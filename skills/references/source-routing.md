# Source Routing Guidance

本文件只回答一个问题：**哪些来源对当前学习价值有直接、具体的匹配，因此值得参与召回。**

它不是平台能力表、登录状态表或下载说明书。当前到底能不能搜、能不能读、能不能下，以运行时真实工具结果为准。

## 1. 路由原则

不要从“哪个平台最好”或“有哪些平台”开始。先判断：

1. 用户要完成什么；
2. 需要哪些内容形态、学习价值或证据角色；
3. 哪些来源对此存在**直接价值匹配**；
4. 在对应来源里，人会怎么搜。

### 来源优势是搜索先验，不是内容边界

平台“通常擅长什么”只用于判断：

- 为什么值得去这里找；
- 什么 query 更自然；
- 结果回来后应重点看什么。

它不能在搜索前推出：

- 另一个平台没有这类内容；
- 这个平台上的内容一定更好；
- 某个具体候选一定适合、公开或可下载。

例如 Bilibili 更常见中长讲解、Douyin 更常见短科普，但这不意味着“火山科普只能搜 Bilibili”。只要两者都对当前 Coverage 有直接匹配，就可以一起召回，最终看真实候选。

### 直接价值匹配即可参与召回

一个来源不需要拥有“其他来源完全没有”的独占职责。

只要能具体回答：

> 这个来源为什么有合理概率为当前 Coverage 提供有价值候选？

就可以参与。

反过来，下面这些理由都不够：

- “平台已经接入”；
- “理论上可能有”；
- “用户是学生”；
- “这个主题也能做成视频/音频”。

搜索阶段偏 Recall，评估阶段偏 Precision。不要在 routing 阶段过早替结果做筛选。

### 宽召回不等于全平台扫描

多个直接匹配来源可以并行搜索，但没有直接匹配的来源不要为了平台数量加入。

优化目标是：

> **减少重复搜索，而不是减少合理来源。**

同一来源的一条自然 query 如果可以同时覆盖相近价值，就合并，不做 `Coverage × Platform` 的机械笛卡尔积。

## 2. OpenClaw `web_search` 与专门生态

### `web_search` 是开放互联网发现能力

这里的 Host Web Search 指 **OpenClaw 原生 `web_search`**。不要在 `education-resources` MCP 中再包装一层通用 Web Search，也不要把它当成专门平台全部失败后的 fallback。

它的优势是跨站发现：官方机构、专业文章、博物馆/出版社/学校/大学/研究机构、教程、地图、活动方案、PDF/PPT/worksheet、未单独接入的长尾网站，以及当前并不知道应去哪个垂直平台找的资源。

典型触发：

- 形式/来源不限；
- 需要专业、官方、原始事实；
- 可能存在有价值的图文、文档、地图或长尾材料；
- 没有单一垂直生态天然覆盖主要需求；
- 用户明确要求“网上找”“网页资料”“全网搜”等开放互联网发现。

典型不触发：

- 用户明确只要某个平台；
- 用户已经给出具体 URL，当前任务只是获取/转换这个 URL；
- 一个窄任务已经被明确专门生态直接覆盖，Web 不会增加明显价值。

开放式 Research 首轮通常应包含 `web_search`，不是为了凑来源，而是因为它承担跨生态发现。

### `web_search` 结果先是候选，不是 MCP Resource

`web_search` 返回的 URL、标题、摘要/片段、来源域名、日期等，只能作为当前搜索证据。不要因为某个结果出现，就自动创建 MCP `resource_id`，也不要把整页搜索结果批量 `resource_import_url`。

先用搜索结果能够支持的事实做候选判断：

- 明显无关 → Reject；
- 看起来有潜力，但缺少会改变决策的页面事实 → Hold；
- 搜索证据已经足够说明值得推荐 → Recommendable。

只有下面几类情况，才把**具体、高潜或用户选中的 URL**交给 `resource_import_url`：

- 用户明确要下载、保存、归档或转换该网页/URL；
- 必须读取/检查页面本体才能决定是否推荐或获取；
- 需要进入 MCP 的 Inspect / Download / HTML Design / Archive 能力。

单纯“给我找几篇资料并推荐”不需要把所有 Web 候选导入 MCP。

### Web 候选与专门平台候选共同竞争

`web_search` 和 `resource_search` 是并列的召回来源，不是“主搜索 / 备用搜索”。同一个 Coverage 可以同时由二者召回。

如果 `web_search` 命中了 Bilibili、CCTV 等已接入平台，而 `resource_search` 又返回同一个实际资源，应按 URL、平台稳定标识、标题/作者等当前证据把它视为**同一个语义候选**，不要向用户重复推荐两次。优先保留信息更完整、后续更容易获取的那份证据即可；不需要创建跨工具持久 ID。

### 专门来源生态

专门平台在某类资源中通常有更高密度召回，也能返回更接近资源本体的结构化候选。相同学习价值可以同时由多个专门来源参与，也可以与 `web_search` 同时参与，只要都有直接匹配。

## 4. 一个价值可以派发多个来源

例如：

```text
用户目标：让孩子理解火山并能直观看到喷发

Coverage A：形成/喷发机制
web_search：火山形成 喷发原理 科普
Bilibili：火山喷发 原理 动画 实验演示
Douyin：火山喷发 原理 科普

Coverage B：喷发过程观察
Bilibili：火山喷发 真实影像 动画
Douyin：火山喷发 现场 科普
CCTV：如果纪录片/真实影像对当前目标有价值，再搜 火山 喷发 纪录片
```

这里不应写成：

```text
机制解释只能 Web
过程观察只能 Bilibili
```

也不应变成：

```text
web_search / Bilibili / Douyin / CCTV / SmartEdu / Ximalaya / Wenku 全部搜索
```

正确模型是：

```text
Coverage Need
  ↓
Direct Value Match
  ↓
Eligible Sources
  ↓
Reasoned Fan-out
  ↓
Real-result Competition
```

### SmartEdu 的边界示例

“给小学生找有趣的火山科普”：

- `web_search`：有直接价值；
- Bilibili：有直接价值；
- Douyin：有直接价值；
- CCTV：如果真实影像/纪录片值得补，可参与；
- SmartEdu：默认没有足够触发信号。

“按小学科学教材找火山相关同步课”：

- SmartEdu：教材/同步/课时信号明确，直接匹配。

所以“用户是学生”不能触发 SmartEdu，“教材同步学习”可以。

## 5. Query 要适应来源，不要复制评价词

同一个主题在不同生态里自然 query 可以不同：

```text
web_search：火山形成 喷发原理 科普
Bilibili：火山喷发 原理 动画 实验演示
Douyin：火山喷发 原理 科普 实验
CCTV：火山 喷发 纪录片
SmartEdu：小学科学 火山 同步课   # 仅在课程信号存在时
```

不要把“儿童火山优质资料”复制到每个平台。

如果一个来源的一条 query 可以同时覆盖“理解 + 观察”，就合并，不要为了每个 Coverage 分别搜一遍。

## 6. 来源集中与 Gap

准备停止开放式任务前，如果高潜候选高度集中，可以问：

> 其他来源是否能补当前候选明显缺少、且对用户目标有价值的内容？

如果能，这是 Coverage Gap。

如果不能，或用户已经限定资源形态/来源，集中不是问题。

明确区分：

> **“还有一个 eligible source 没搜”本身不是 Gap。**

Gap 必须来自当前结果暴露出的缺失价值，而不是平台清单。

例如：

- 只有大量火山短视频，但缺可靠结构化解释 → 补 `web_search` / 长解释路线；
- 已有可靠 Web 科普 + 合适动画 + 优质短解释 → 不因为 CCTV 尚未搜就必须继续；
- 用户只要真实喷发视频 → 全是视频正常；
- 用户要教材同步课 → SmartEdu 集中完全合理。

## 7. 三类事实不要混淆

始终区分：

- **来源生态知识**：通常擅长什么、什么信号值得触发；
- **当前能力事实**：本次运行是否能搜索/访问；
- **当前候选事实**：具体资源是否公开、完整、适合、可获取。

来源生态只决定“为什么值得搜、怎么搜”，不能自动推出登录、可用性、结果质量或下载事实。

`web_search` 的 snippet/摘要也只是搜索证据，不能自动当成页面全文事实；需要页面本体才能确认的关键判断，应进入必要的读取/Import/Inspect，而不是靠摘要补全。

## 8. 创作者内容

只有用户真正关心某个创作者/账号已有内容时，才进入创作者浏览或完整枚举。

“提到作者名字”不自动等于浏览作者主页；普通主题搜索也不应自动升级成 creator browse。

只想挑代表作时，小规模预览即可；明确要求全部作品时，再按完整枚举任务处理。
