# resource-intent

## 目标

把自然语言需求编译成稳定的语义模型，同时保留模型对语境、隐含目标和歧义的理解能力。

Schema 约束输出结构，不替代语义推理。不要为了满足字段而编造事实；未知值是合法结果。

本阶段要回答的是：

1. 用户究竟想让孩子学什么、解决什么问题或获得什么资源？
2. 哪些要求是必须满足、偏好满足或明确排除？
3. 现有信息是否足以让 Search 设计一个不会明显跑偏的搜索计划？
4. 如果不足，只澄清那个最可能让搜索方向发生根本变化的问题。

澄清不是为了收集完整的孩子档案，也不是为了把所有槽位填满。

## 输入与输出

文件 envelope、字段类型和阶段交接以 `../docs/pipeline-data-contract.md` 为统一契约。

- 输入：`{session_dir}/request.json`，契约见 `schemas/input.schema.json`。
- 输出：`{session_dir}/stage1_intent.json`，契约见 `schemas/output.schema.json`。
- 输出版本：`intent-spec/v1`。

`request.json` 是本阶段唯一事实快照。读取：

- `data.raw_request`：当前原始需求。
- `data.conversation_evidence`：与当前需求有关的历史话语。

不要从快照以外的聊天记忆补充事实。目录不存在或输入不符合契约时，返回错误给 flow，不自行创建会话或生成 session ID。

## 推理原则

1. **用户原话优先**：明确表达永远覆盖常识、模板和默认值。
2. **语义优先**：理解“找点题练练手”意味着练习目标，不依赖关键词硬匹配。
3. **证据可追溯**：`explicit` 和 `inferred` 都要记录支持它的短文本证据。
4. **推断与事实分开**：合理推断标记 `inferred`，低风险补全标记 `defaulted`。
5. **未知优于臆测**：无法可靠判断时省略该槽位，不要用空对象或看似完整的错误值填满结构。
6. **动态调整**：根据主题、表达方式、上下文和约束决定抽取深度，不要求每次需求都具有相同信息量。
7. **不提前做搜索决策**：不选择平台、不生成可执行查询、不写 `site:`、不分配查询数量。

完整槽位语义和推断边界见 `references/semantic-rules.md`。处理资料类型、具体形态或文件格式时必须读取 `references/resource-form-rules.md`；只有在主题概念归一化不确定时读取 `references/domain-vocabulary.md`。

## 执行流程

### 1. 建立证据优先级

按以下顺序处理冲突：

1. 当前 `raw_request`
2. 当前需求相关的 `conversation_evidence`；较新的用户回答可以补充或修正原始请求
3. 有充分语义依据的推断
4. 低风险默认值

如果两条用户证据互相冲突，不替用户决定；判断冲突是否会改变搜索方向，必要时澄清。

### 2. 先提取约束，再提取偏好

把自然语言要求分成：

- `constraints.must`：不满足就不应推荐，例如“必须带答案”“只要免费的”。
- `constraints.prefer`：可以妥协，例如“最好可打印”“优先官方”。
- `constraints.exclude`：明确排除，例如“不要视频”“不要付费内容”。

不要把“最好”“优先”升级为必须，也不要把默认偏好伪装成用户约束。

### 3. 抽取并归一化槽位

每个槽位输出：

```json
{
  "value": "小学四年级",
  "status": "explicit",
  "evidence": ["四年级数学课程"]
}
```

状态含义：

- `explicit`：用户直接表达或明确确认。
- `inferred`：可由语义或字段关系可靠推出。
- `defaulted`：为继续流程使用的低风险默认。

不输出主观置信分。`status + evidence` 已足以区分事实、推断和默认值。只输出有值的槽位；未知槽位直接省略。

年龄和年级可以互相推断，但必须标记 `inferred`；教材版本、付费接受度、资料类型等不能只凭主题擅自推断。

资料相关信息必须分层记录，不能压成一个字段：

- `resource_types`：资料大类，例如视频类、音频类、文档类、练习类、图文类、图片类。
- `format_preferences`：用户说出的具体内容形态，例如动画、纪录片、公开课、试卷、练习册、绘本、课件。
- `file_formats`：实际文件格式，例如 PDF、PPTX、DOCX、EPUB、MP3、MP4。

一个资源可以属于多个大类。例如“PDF 数学试卷”应保留 `resource_types=["文档类", "练习类"]`、`format_preferences=["试卷"]`、`file_formats=["PDF"]`。“可打印”是使用或交付约束，不是文件格式；按语气写入 must 或 prefer。

用户没有直接说明，且上下文或使用场景也不足以可靠推出资料类型、具体形态或文件格式时，省略对应槽位，不要替用户默认成视频、图文或文档。Search 负责依据主题规划多形态覆盖。用户明确说“形式不限”“什么类型都可以”时，记录 `resource_types=["不限"]` 且标记 `explicit`，这与没有提供信息不同。

### 4. 判断是否澄清

按顺序通过四道门判断：

| 判断门 | 需要澄清 | 不需要澄清 |
|---|---|---|
| 学习对象 | 只有"找点学习资源""孩子学不好"，无法形成具体学习对象 | 已能形成"恐龙科普""四年级数学课程""情绪管理绘本"等主题 |
| 资源类型 | "找三年级数学学习资料"——"学习资料"过于笼统，可能指向视频课程、练习试卷或知识点文档等完全不同的搜索方向 | 用户已说了具体形态，如"课程""试卷""动画""文档""视频" |
| 语义分叉 | "编程""英语""国学"等可能指向差异很大的学习路线，且上下文不能消歧 | 虽有多个细分方向，但可以用多角度搜索共同覆盖 |
| 事实冲突 | 年龄与年级、教材版本、必须条件之间出现明确冲突 | 仅缺少年龄、平台、形式或排序偏好 |
| 硬约束 | must 与 exclude 互相冲突，或必须条件无法判断真实含义 | 只是"最好""优先""有的话"等软偏好 |

只要能确定"主要学习对象 + 不可违反的约束"，通常就可以进入 Search。不要因为以下信息缺失而自动追问：

- 没说年龄，但主题本身已经明确且不涉及明显适龄风险。
- 没说视频、音频或文档；Search 可以多形态覆盖，Selector 可以让用户选择。**但注意**：如果用户用"学习资料""材料"等泛词而非具体形态词，且主题不暗示某种类型，则按"资源类型"判断门处理。
- 没指定平台；平台选择本来就是 Search 的职责。
- 没说难度；可以省略，或在低风险场景采用透明默认。
- 没提供所有背景原因；只要目标已经可搜索即可。

必须优先澄清的对象按顺序是：

1. 无法确定的核心学习对象或问题。
2. 会把搜索带向完全不同内容类型的语义分叉。
3. 相互冲突的用户明确事实。
4. 相互冲突或含义不清的 must/exclude 条件。
5. 只有在确实会改变内容安全、难度或媒介时，才澄清年龄、基础或使用场景。

使用“影响测试”：如果不问，Search 是否很可能搜索到另一类资源？如果只是候选排序不同，不问。

- 会显著改变：`status=needs_clarification`。
- 只影响排序或可后续筛选：省略未知槽位或使用透明默认，`status=ready`。

澄清只问一个影响最大的自然语言问题，不把多个问题拼在一起。详细规则见 `references/clarification-rules.md`。

示例：

- "想让孩子学编程" → 问 Scratch、Python 还是机器人，因为路线完全不同。
- "孩子数学不好" → 问最想解决哪类问题，例如计算、应用题或概念理解。
- "找恐龙科普，形式都行" → 不问年龄和形式，先搜索多形态候选。
- "四年级数学课程" → 不问具体年龄或教材版本，当前主题已经足以规划。
- "不要视频，最好路上听" → 不问形式，已可推断音频方向并记录证据。
- "6 岁的四年级孩子" → 澄清年龄和年级冲突，因为会改变难度判断。
- "找三年级数学学习资料" → 问更偏向哪种资料（视频课程讲解、练习试卷、知识点文档），因为"学习资料"过于笼统，不同方向的搜索策略和结果完全不同。
- "找几道数学练习题" → 不问，用户已说清要练习类。

需要澄清时仍写入当前部分语义结果：

```json
{
  "_summary": {
    "status": "needs_clarification",
    "question": "你说的编程更偏向 Scratch 动画，还是机器人编程？"
  },
  "data": {
    "status": "needs_clarification",
    "clarification": {
      "question": "你说的编程更偏向 Scratch 动画，还是机器人编程？",
      "reason": "两种方向会使用不同资源和平台"
    }
  }
}
```

写完后停止，不生成 Search 输入。Flow 负责向用户提问、更新 `request.json` 并重新调用本 Skill。

### 5. 生成搜索概念，不生成查询

当状态为 `ready` 时，输出：

- `canonical_terms`：需求不可丢失的规范概念。
- `synonyms`：同义词、常见别称。
- `related_terms`：有助于召回但不等同于核心需求的相关概念。

这些只是供 Search 动态生成查询的语义材料。不得包含平台选择、`site:`、任务优先级或完整搜索句。

### 6. 记录假设

每个 `defaulted` 槽位都必须在 `assumptions` 中有对应的人类可读说明。没有默认假设时省略 `assumptions`；不要把 `inferred` 混入默认假设。

### 7. 写入并校验

写入精简 envelope：

```json
{
  "_meta": {
    "schema_version": "intent-spec/v1",
    "session_id": "继承 request.json",
    "created_at": "ISO 8601"
  },
  "_summary": {
    "status": "ready"
  },
  "data": {
    "status": "ready",
    "raw_request": "用户最初请求原文",
    "slots": {},
    "constraints": {},
    "search_concepts": {}
  }
}
```

运行：

```bash
python scripts/validate_output.py {session_dir}/stage1_intent.json
```

校验失败时，根据错误修复输出一次并重新校验。第二次仍失败则向 flow 返回结构化失败，不得继续 stage 2。

## 完成条件

- `ready`：结构校验通过，flow 可以调用 resource-search。
- `needs_clarification`：结构校验通过，flow 必须先向用户提问。
- 只向 flow 返回 `_summary` 和输出路径，不直接向用户展示完整 Intent。
