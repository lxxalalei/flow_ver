# Intent 澄清决策与话术规则

## 1. 澄清的唯一目的

澄清是为了避免 Search 搜到另一类资源，不是为了完成问卷。只问“现在不确认就很可能走错方向”的信息。

判断句：

> 如果不问这个问题，是否仍能生成一个合理、可筛选、不会明显偏离用户诉求的搜索计划？

- 能：不问，省略未知槽位，或使用有证据的 inferred、透明默认继续。
- 不能：澄清一个影响最大的点。

## 2. 澄清优先级

### P0：核心学习对象无法确定

必须问：

- “帮我找点学习资源”
- “想让孩子多了解一些”
- “想提升一下”但没有说明要提升什么

问题应让用户描述真实主题或痛点：

- “目前最想让孩子了解或学习什么？”
- “最想解决的是哪个具体问题？”

不要先问年龄、平台或资源形式。

### P0：多个目标无法共同处理

当用户同时提出彼此独立的主题，并且一组搜索计划无法合理覆盖时，只确认本次先处理哪个主题。单个宽泛主题仍然可以由 Search 使用多个角度探索，不要为了提前限定路线而追问。

### P0：用户明确事实冲突

例如：当前表达与已经确认的使用者条件、资源要求或版本信息无法同时成立。

问题应直接指出冲突并让用户确认哪一个有效，不要自行选择更常见的答案。

### P0：硬约束冲突

例如：

- “只要免费的，付费课程也可以”
- “不要视频，最好找动画”
- “必须可打印，只想要音频”

确认真正不能妥协的条件。软偏好之间可以并存，不需要澄清。

### P1：学习者信息确实改变内容路线

使用者信息通常不是第一问，但以下情况值得问：

- 同一主题面向不同年龄时，内容尺度、理解门槛或安全要求差异巨大。
- 用户要求“孩子自己看”，适龄和安全要求会直接影响候选。
- 缺少使用者信息会使资料无法安全、有效地使用。

以下情况不追问使用者信息：

- 主题可以多年龄覆盖并由 Selector 标注。
- 用户只是先看候选。

### P1：场景会决定资源媒介

只有资源形式会因此完全改变时才问：

- “想找英语材料”但已知场景是开车时使用 → 可直接推断音频，不问。
- “想找亲子活动”但不清楚是在家操作还是课堂使用 → 场景可能决定材料类型，可问。

## 3. 不应该澄清的情况

- "找恐龙学习资料"——主题已经可搜索，由 Search 规划互补形态。
- "想让孩子学编程"——先搜索适合儿童入门的不同方向，不要求用户先选路线。
- "推荐一些古埃及文明学习资源"——先用标准模式探索讲解、阅读和沉浸式内容。
- "你看着办""随便推荐"——采用透明默认，不要把决定权退回用户。
- "最好官方"——这是 prefer，不需要确认是否完全排除非官方。
- 没指定平台——平台路由属于 Search。
- 没指定数量——搜索预算属于 Search。
- 没指定下载格式——可在 Selector/Downloader 阶段处理。
- 用户没有指定资源形态——由 Search 选择与主题相关的互补方向。

## 4. 一次只问一个问题

错误：

> 想了解什么主题、孩子多大、喜欢视频还是音频、要不要付费？

正确：

> 目前最想让孩子了解或解决的具体内容是什么？

即使存在多个未知信息，也只问影响最大的一个。用户回答后重新运行 Intent，再判断是否还存在 P0 歧义。

## 5. 问题表达

问题应包含：

1. 用户能理解的自然语言。
2. 当前最可能的 2-3 个方向，帮助快速回答。
3. 允许自由回答，不强迫选固定分类。

示例：

- “目前最想让孩子了解或学习什么主题？”
- “这次最想先找鸟类观察资料，还是绘画入门资料？”
- “前后两条要求无法同时满足，这次以哪一条为准？”
- “你说不要视频但希望有动画，实际是完全不要视频，还是可以接受短动画讲解？”

不要说“请补充槽位”“请选择资源分类”“为了精准推荐请填写以下信息”。

## 6. 澄清结果结构

```json
{
  "data": {
    "status": "needs_clarification",
    "clarification": {
      "question": "目前最想让孩子了解或学习什么主题？",
      "reason": "当前请求还没有可用于搜索的主题"
    }
  }
}
```

`reason` 解释为什么必须问。已有槽位已经表达当前掌握的信息，不再额外维护 ambiguity 和 missing-information 列表。

## 7. 持续澄清与停止条件

- 不设置固定澄清轮数。每轮只询问当前影响最大的一个问题，收到回答后重新读取完整 evidence 并再次判断。
- 新证据足以形成合理搜索需求时立即返回 `ready`，不要继续收集可选信息。
- 用户不知道某项信息但授权继续时，省略非关键维度，或在安全且不会明显改变需求时使用透明的低风险默认。
- 核心主题、硬约束或安全条件仍无法确定时继续返回 `needs_clarification`，不要为了结束循环编造信息。
- 用户明确取消、拒绝继续提供必要信息或表示无法完成澄清时，将决定权交回 Flow；Intent 不擅自输出 `ready`。

## 8. 最终检查

提出问题前检查：

1. 不问时是否仍能生成合理、可筛选且不会明显偏离诉求的候选？
2. 是否可以通过互补召回和 Selector 选择解决？
3. 是否误把辅助维度未知当成必须澄清？
4. 是否一次问了多个问题？
5. 是否已有上下文证据可以回答？
