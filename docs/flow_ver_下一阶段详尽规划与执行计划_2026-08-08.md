## 0. 文档定位与结论

本文件不是新的架构重写方案，而是针对当前 flow_ver 分支已完成的 0017–0023 实现，给出下一阶段可直接执行的收口规划。核心原则是：暂停继续堆叠新工具和新平台，把系统从“架构闭环已经搭起来”推进到“检索判断可信、能力语义准确、真实 OpenClaw 链路可验收、版本有明确发布门禁”。

| 项目 | 当前事实 | 本计划处理方式 |
| --- | --- | --- |
| 公共协议 | `contract_version = 1.0.0` | 保持不变，优先使用兼容加法；除非出现不可兼容语义才讨论 2.0 |

## 1. 当前架构基线：后续开发必须以此为 Source of Truth

后续任何 Codex 任务开始前，先确认机器事实而不是从历史设计文档推断。Source of Truth 优先级固定如下：

```text
1. contracts/tool-catalog.json + JSON Schema
2. server.py 实际 @server.tool 注册
3. Python runtime / storage migrations / tests
4. contracts/platforms/platform-registry.json
5. docs/CURRENT_ARCHITECTURE.md
6. docs/DEVELOPMENT_PLAN.md
7. .agent/plans/*
8. legacy/* 仅作迁移与回滚证据，不得覆盖 active runtime
```

当前 active 主链保持：

```text
自然语言
  -> learning-resource-flow Skill
  -> education-resources stdio MCP
  -> ResourceService
  -> Search Adapter / Inspection Router / Acquisition Router
  -> SQLite 权威状态 + 受控文件

业务状态：
FlowTask
  -> ResultSet
  -> Presentation
  -> Selection
  -> DownloadPlan
  -> Job
  -> AssetBundle / BundleItem
  -> Asset
  -> Archive

候选核验：
CandidateResource
  -> resource_inspect
  -> ResolvedResource
  -> Representation
  -> Resolution
  （Resolution 不改写不可变 ResultSet）
```

本计划不改变上述主链，不重新引入旧七 Skill 流水线，也不把平台脚本直接暴露为 Tool。

## 2. 审查后确认的主要问题

| 优先级 | 问题 | 风险 | 目标状态 |
| --- | --- | --- | --- |
| P0 | Coverage 对缺少语义证据的候选偏乐观 | 低质量召回可能被过早判定为 `coverage_sufficient`，导致过早 Present | 无证据默认 UNKNOWN/WEAK；事实 Coverage 与模型 Semantic Review 分层 |
| P1 | Platform Registry 的 `acquire=true` 语义过宽 | 只能保存落地页的平台可能被误解为可获取资源本体 | 显式区分 `primary_resource / representation / landing_page / metadata` |
| P1 | SearchDirection / direction 字段的文档与 Schema 存在语义漂移 | 模型与服务端对 provenance 的权威性理解不一致 | 明确 direction 是“模型提供的非权威执行标签”，或从 public schema 移除 |
| P1 | Coverage schema 与内部 evaluator 维度存在漂移风险 | 契约声明与运行时事实长期分叉 | 建立 schema/runtime consistency test，字段一处变更多处自动失败 |
| P1 | 0023 未完成真实 OpenClaw 最终验收 | 本地 E2E 通过但 Agent 实际工具编排仍可能失败 | doctor/probe + 真实 Agent 回合 + 至少一组真实平台矩阵 |
| P2 | 缺少稳定 Retrieval Benchmark | 每次调 Coverage/Skill/Adapter 后难判断质量到底提升还是回退 | 建立固定任务集、人工 gold 与机器指标，作为 release gate |
| P2 | WebBundle 存储形式与最终用户打开体验尚未完全解耦 | 资料库可能只展示 ZIP，而不是可直接阅读的 HTML | 底层继续 Bundle 存储，上层 Viewer 以 `index.html` / primary representation 打开 |

## 3. 下一阶段总目标与非目标

### 3.1 总目标

- 让系统能可靠回答三个问题：搜到的候选是否真的支撑当前目标；是否还存在会改变推荐结果的关键 Gap；继续搜索是否有实际信息增益。
- 让 Registry 对“搜得到、看得懂、核验得到、资源本体拿得到、只能保存页面”分别表达，不再使用一个模糊 acquire 布尔值覆盖全部语义。
- 让 OpenClaw 真实 Agent 使用同一套 13 Tool 完成完整链路，而不是只在 Python fixture / Service 层通过。
- 建立固定 Benchmark 与发布门禁，使以后新增 Adapter、Inspector、Materializer 或平台能力时能量化回归。

### 3.2 明确非目标

- 本轮不新增第 14 个 MCP Tool。
- 本轮不新增平台数量，不以“多接平台”作为完成指标。
- 本轮不开发远程 Streamable HTTP MCP，不做生产多租户改造。
- 本轮不把 LLM 评分伪装成服务端确定性事实。
- 本轮不把真实 URL、Cookie、Token、文件路径重新暴露给模型。
- 本轮不为了提高 Coverage 而放宽 SSRF、认证、DRM、付费墙或访问控制边界。

## 4. 目标判断模型：Factual Coverage + Semantic Review + Stop Controller

下一阶段最核心的结构调整不是增加一个新的 Tool，而是重新定义“谁有资格判断什么”。服务端负责确定性事实；模型负责语义判断；Controller 负责把两类证据与策略边界合并成 StopDecision。

```text
                    Search / Inspect
                         │
                         v
                ┌──────────────────┐
                │ Factual Evidence │
                │ 服务端可验证事实 │
                └────────┬─────────┘
                         │
             ┌───────────┴───────────┐
             │                       │
             v                       v
     Factual Coverage           Candidate Payload
  availability/source/...            │
             │                       v
             │                ┌───────────────┐
             │                │ SemanticReview│
             │                │ LLM 语义审查  │
             │                └───────┬───────┘
             └───────────────┬────────┘
                             v
                    ┌────────────────┐
                    │ Stop Controller│
                    │ Present/Replan │
                    │ Clarify/Gap    │
                    └────────────────┘
```

### 4.1 服务端 Factual Coverage 应判断的内容

| 维度 | 服务端可以权威判断 | 服务端不应擅自判断 |
| --- | --- | --- |
| availability | HTTP/平台状态、Resolution availability、认证/策略阻断 | 内容“值不值得看” |
| representation | 是否有 HTML/PDF/EPUB/MP4/MP3/页面表示、是否可合法获取 | 该表示是否最适合当前学习目标 |
| source diversity | 来源族数量、去重后的 provider/platform provenance | 来源在某具体问题上的专业程度 |
| constraint evidence | 格式、语言、来源、日期等可机器核验硬条件 | 含糊的“适合孩子”“深入”“有趣” |
| identity/dedup | native ID / ISBN / DOI / canonical URL / conservative weak fingerprint | 两个语义相近但不同资源是否应该合并 |
| failure/gain | 新增唯一候选、重复数、失败数、Gap 的机器事实闭合 | “这轮搜索有启发性”这种主观判断 |

### 4.2 SemanticReview 应判断的内容

SemanticReview 由 Skill/LLM 根据当前 task、候选标题/摘要、必要的 Inspection 结果生成。它不是新 MCP Tool，也不是服务端权威状态。建议结构化为内部对象并保留可解释理由，但不写入公共契约。

```text
SemanticReview {
  resource_id
  relevance: pass | weak | fail
  usefulness: pass | weak | fail
  target_fit: pass | unknown | fail
  constraint_fit: pass | unknown | fail
  substantive: pass | weak | fail
  evidence_level: search_only | inspected
  reasons[]
}
```

关键规则：Search-only 候选可以被推荐，但若任务对可用性、版本、内容深度或资源本体获取有明确要求，则没有 Inspection 证据时不能自动升级为 `confirmed`。

### 4.3 Coverage 状态语义重新收紧

| 状态 | 新定义 | 禁止的捷径 |
| --- | --- | --- |
| UNSEARCHED | 当前必要维度尚未执行相关路线 | 不能因为有其他类型候选而升级 |
| UNKNOWN | 已搜到候选，但没有足够事实/语义证据证明该维度 | 不能等价于 COVERED |
| WEAK | 存在部分证据，但不足以支持最终选择 | 不能仅靠候选数量升级 |
| COVERED | 至少一个可展示候选同时满足必要机器事实 + SemanticReview 通过 | 不能只因有 title / 非 unavailable 就升级 |
| CONFIRMED | 必要情况下经过 Inspection 或强机器证据确认 | 不能由模型口头声称 |

如果为了兼容暂时不新增 UNKNOWN/CONFIRMED 枚举，也应至少采用保守映射：无证据 -> WEAK；明确核验通过 -> COVERED。不要让“无反证”自动等于“有证据”。

## 5. 0024 — Retrieval Quality Calibration

0024 是下一阶段第一优先级。目标是修正 Adaptive Retrieval 的过早停止问题，同时不破坏当前 ResultSet 不可变、extend、幂等、Resolution 与 Tool contract。

### 5.1 0024 工作包

| ID | 任务 | 主要改动位置 | 产出 | 验收 |
| --- | --- | --- | --- | --- |
| 0024-A | 冻结现状与负例 | tests/fixtures, adaptive tests | 新增“低质量但有标题”“无 semantic evidence”“来源单一”“错误 target”负例 | 旧 352 回归不减少，新负例在旧逻辑下能暴露问题 |
| 0024-B | 收紧 displayable 判定 | retrieval/adaptive.py | displayable 只表示“可展示结构完整”，不再隐含 relevance/target covered | displayable_count 与 coverage target 解耦 |
| 0024-C | 重写 coverage evidence 聚合 | retrieval/adaptive.py | 每个维度明确 evidence source；无证据 -> weak/unknown | 无显式证据时不返回 coverage_sufficient |
| 0024-D | 引入 SemanticReview 输入层 | Skill + evaluator private model | 模型审查结果作为 private evaluation input，不成为 MCP public schema | 同一事实输入可复现 StopDecision；模型不能伪造 provenance |
| 0024-E | 重写 StopDecision 门槛 | adaptive.py | Present 必须满足 selection_min + required coverage + semantic pass | 低质量候选不再因数量足够 Present |
| 0024-F | 补 Gap 生成规则 | adaptive.py / docs | semantic_gap / availability_gap / source_gap 等明确边界 | Gap 只表示会改变决策的必要未知 |
| 0024-G | 一致性测试 | tests | Coverage enum / schema / docs / runtime 一致性测试 | 任何字段漂移 CI 失败 |
| 0024-H | Skill 文档同步 | SKILL.md / references | 明确 factual vs semantic 权威边界 | Skill 不把自身判断伪装为 MCP coverage |

### 5.2 0024 决策规则

```text
Present =
  displayable_candidates >= selection_min
  AND all required factual dimensions >= WEAK/COVERED（按任务定义）
  AND required SemanticReview dimensions PASS
  AND no critical Gap
  AND no unresolved constraint that can change selection

Replan =
  exists actionable Gap
  AND budget_remaining > 0
  AND next direction can plausibly close that Gap
  AND no_gain_streak < 2

Clarify =
  only when a missing user fact materially changes the search space
  e.g. 教材同步所需年级/册次、明确互斥约束

StopWithGap =
  critical/important Gap remains
  AND no safe/high-value direction exists
  OR round budget exhausted
  OR policy/auth/unsupported boundary blocks required evidence
```

### 5.3 0024 必须增加的回归案例

| 案例 | 输入特征 | 预期 |
| --- | --- | --- |
| 标题相关但正文不相关 | 5 条 title 命中，Inspection/semantic fail | 不能 Present；应 Replan 或 StopWithGap |
| 只有一个来源族 | 多个候选均来自同平台，任务要求横向比较 | source_diversity gap |
| 教材同步但缺少版本 | 用户明确同步教材，未给册次 | Clarify，且只问最小必要问题 |
| 公开可看但不能获得资源本体 | book/video landing page 可保存 | 可展示，但 acquisition coverage 仍 weak/landing-page-only |
| 高质量 search-only | 摘要已经足够用于“有哪些资源”的探索任务 | 允许 Present，不强制 Inspect 全量候选 |
| 下载前版本不确定 | 书籍同名多版本 | 必须 Inspect 关键候选，未确认版次不进入 confirmed |
| 连续两轮零增益 | new_unique=0 且无 gap closed | 停止；根据 Coverage 选择 Present 或 StopWithGap |
| 认证失败 | required platform AUTH_REQUIRED | 不解释为“没有资源”；Clarify/StopWithGap/合法登录恢复 |

### 5.4 0024 退出条件

- 旧本地测试全绿；新增 quality negative cases 全绿。
- 任何“候选数量足够但没有相关/目标证据”的 fixture 都不能得到 `coverage_sufficient`。
- Skill 与服务端对 Coverage 权威性的措辞一致。
- ResultSet 不可变、extend、Inspection cache、Acquisition、Archive 均无行为回退。
- contract_version 仍保持 1.0.0；若完全通过 private/internal 改动完成，不提升 catalog_version。

## 6. 0025 — Platform Capability Contract Alignment

0025 解决 Registry 中 `acquire=true` 的语义模糊，以及 SearchDirection / Coverage schema 与 runtime 的漂移。目标是让 Planner 在看到平台能力时能够区分“资源本体”“某种 representation”“落地页”“仅元数据”。

### 6.1 Acquisition Scope 设计

推荐保留 `capabilities.acquire` 作为兼容总开关，但增加结构化 acquisition scope。

```json
{
  "capabilities": {
    "search": true,
    "inspect": true,
    "acquire": true
  },
  "acquisition": {
    "scopes": [
      "primary_resource",
      "representation",
      "landing_page",
      "metadata"
    ],
    "strategies": ["platform_video", "webpage"]
  }
}
```

| scope | 定义 | 示例 |
| --- | --- | --- |
| primary_resource | 可以合法获取用户真正选择的资源本体 | 公开视频 MP4、公开 PDF/EPUB、公开音频 |
| representation | 可以获取同一逻辑资源的受控表示，但未必是原始本体 | 转写、字幕、清洗 HTML |
| landing_page | 只能把承载资源描述/阅读体验的页面物化 | 图书馆书目页、课程介绍页 |
| metadata | 只能保留描述性元数据或索引信息 | ISBN/作者/版本/目录信息 |

### 6.2 平台迁移规则

逐平台按实际 downloader/materializer 行为标注，不以 resource_type 推断 scope。一个平台声明 video/book/course 不代表拥有 primary_resource 获取能力。

| 平台类型 | 典型迁移 | Planner 应如何解释 |
| --- | --- | --- |
| 专用媒体 downloader 已接入 | `primary_resource + landing_page`（如页面可物化） | 可以计划资源本体获取，但仍受 auth/policy 约束 |
| 仅 webpage strategy | `landing_page`；必要时 `metadata` | 只能保存页面，不得承诺视频/图书/课程本体 |
| Inspector 可解析多个 representation | `representation + 对应可获取 scope` | 先 Inspect 决定表示，再准备获取 |
| 搜索聚合/书目索引 | `metadata / landing_page` | 用于发现与比较，不等于可下载 |

### 6.3 direction 字段收口

建议保留 `SearchTask.direction`，但正式定义为“模型提供的非权威执行标签”。它用于解释一条 query 属于哪个 SearchDirection、要关闭哪个 Gap；服务端只存 provenance，不将其升级为 coverage 事实。

```text
direction:
  source = model
  authority = advisory
  server_behavior = persist-as-provenance-only
  forbidden = cannot close Gap / cannot mark Coverage by itself
```

如果现有代码没有可靠使用场景，则第二选择是从 public schema 移除。禁止维持“Schema 允许、Skill 文档禁止”的灰色状态。

### 6.4 Schema/runtime consistency gate

- tool-catalog 中工具数与 server.py 注册工具精确一致。
- 公共 resource_type 枚举、runtime normalizer、Registry resource_types 一致。
- Coverage dimension 的 schema、Python enum、serializer、tests 精确一致。
- Registry `capability.inspect` 与 Inspection Router 实际实现精确一致。
- `acquisition.strategies/scopes` 与实际 provider/router 能力一致；不存在只靠文档声称的能力。

### 6.5 0025 退出条件

- 16 个平台全部完成 acquisition scope 迁移并通过 schema。
- Planner/Skill 文档不再使用模糊的“acquire=true = 可下载资源本体”表述。
- direction 字段形成唯一明确语义。
- 新增 Registry/runtime consistency tests；任一平台声明与代码能力漂移时测试失败。

## 7. 0026 — Real OpenClaw & Real Platform E2E

### 7.1 环境预检

```text
openclaw --version
openclaw config validate --json
openclaw mcp status --verbose
openclaw mcp doctor education-resources --probe
openclaw mcp probe education-resources --json
```

- 确认 OpenClaw 实际加载当前工作区而不是旧同步目录。

### 7.2 真实 Agent 对话矩阵

| 场景 | 自然语言任务 | 必须观察的工具链 | 通过标准 |
| --- | --- | --- | --- |
| 文章 | 找一篇中文图文科普文章，先看再决定是否保存 | flow_start -> search -> optional inspect -> presentation | 不提前下载；候选相关；展示后状态可恢复 |
| 网页物化 | 保存一篇图文网页供离线阅读 | selection -> prepare -> confirm -> start -> job_status -> archive | HTML/MD/同源图片关系完整；ZIP 仅为存储容器 |
| 视频 | 找并保存公开视频 | search -> inspect if needed -> platform acquisition | 若只能 landing page 必须明确说明；有 primary_resource 才承诺媒体本体 |
| 音频 | 找一条可离线收听的音频资源 | search -> inspect -> acquisition | 媒体格式与 role 正确，无假 primary |
| 图书 | 找指定版本图书，能拿到正文才下载 | search -> inspect edition/representation | 只有书目时明确 metadata/landing_page；不能把书目页当书 |
| 课程 | 找包含视频+PDF的课程 | Search/Inspect -> multi-asset Bundle | Bundle roles、partial、Archive 关系正确 |
| 混合检索 | 对同一主题给文章+视频+可打印材料 | 多方向 search -> extend -> selective inspect | Gap 驱动 Replan；不是无差别全平台搜索 |
| 恢复 | 中断后继续刚才任务 | flow_status / job_status | 不丢选择/计划；不自动重放网络副作用 |

### 7.3 真实平台验收分级

不要把“Adapter 已注册”与“平台生产可用”混为一谈。建议每个平台记录以下状态：

```text
code_present
fixture_passed
network_smoke_passed
auth_flow_passed
inspect_passed
acquisition_passed
policy_reviewed
production_ready
```

只有最后一项为 true 才可以在用户文案中描述为稳定支持。否则使用“已接入/实验性/当前可搜索”等更准确措辞。

### 7.4 0026 退出条件

## 8. 0027 — Retrieval Benchmark & Release Gate

Benchmark 的目的不是追求一个漂亮总分，而是让每次修改可以回答：相关性是否提高、早停是否减少、Gap 是否更准确、平台能力是否被误承诺。

### 8.1 Benchmark 任务集

| 任务族 | 最低覆盖 | 典型目标 |
| --- | --- | --- |
| 窄目标查找 | 10+ cases | 指定主题/格式/来源，验证 precision |
| 宽泛探索 | 10+ cases | 验证多方向但不无差别全搜 |
| 混合资源 | 10+ cases | article/video/document/book/course 组合 |
| 教材同步 | 8+ cases | 需要/不需要澄清的边界 |
| 版本与表示 | 8+ cases | 书籍版本、PDF/EPUB、网页落地页 |
| 来源可信度 | 8+ cases | 官方/专业/社区来源差异 |
| 认证与策略 | 8+ cases | AUTH_REQUIRED、unsupported、policy block |
| 低质量负例 | 10+ cases | 标题党、聚合页、重复、无正文、错误 target |
| 网页物化 | 8+ cases | 纯文本、图文、长文、代码、表格、复杂结构 |
| 恢复与状态 | 6+ cases | 跨回合、重启、幂等、Selection/Plan 失效 |

### 8.2 建议指标

| 指标 | 定义 | 用途 |
| --- | --- | --- |
| Top-N Relevance Precision | 展示候选中人工 gold 判定相关的比例 | 防止候选数量掩盖质量 |
| Premature Present Rate | 仍有关键 Gap 却返回 Present 的比例 | 核心 P0 指标 |
| Unnecessary Replan Rate | Coverage 已足够却继续搜索的比例 | 控制成本与对话长度 |
| Gap Precision | 生成的 Gap 中真正会改变选择的比例 | 避免所有未知都变 Gap |
| Gap Recall | gold 标注的重要 Gap 是否被识别 | 避免漏掉版本/可用性/来源缺口 |
| Inspect Efficiency | 被 inspect 的候选中真正改变决策的比例 | 避免全量 Inspect |
| Acquisition Truthfulness | 承诺“可获取本体”的资源中实际成功获取本体的比例 | 验证 Registry scope |
| Dedup Accuracy | 逻辑重复合并正确率 + 误合并率 | 保护 ResultSet 质量 |
| E2E Completion | 自然语言任务完整走到目标状态的比例 | 验证 OpenClaw 编排 |

### 8.3 Release Gate

建议版本进入“可继续扩平台”阶段前，至少满足：

- Premature Present Rate 在关键负例上为 0；普通 benchmark 明显低于当前基线。
- 任何 landing_page-only 平台都不会被测试判为 primary_resource acquisition 成功。
- OpenClaw E2E 六大类场景全部通过；失败场景也要验证解释和恢复正确。
- 全量 unit/contract/storage/stdio E2E 继续全绿。
- CURRENT_ARCHITECTURE、DEVELOPMENT_PLAN、Registry、Skill 与 runtime 无已知语义漂移。

## 11. 测试与验收矩阵

| 层级 | 测试对象 | 必须覆盖 | 失败意味着什么 |
| --- | --- | --- | --- |
| Unit | adaptive / identity / dedup / models | 状态转换、边界、异常输入 | 算法或数据模型错误 |
| Contract | 13 tools / schema / catalog | 输入输出、版本、tool count | 公共兼容性风险 |
| Registry | 16 platform capabilities | schema + runtime descriptor + scopes | 能力声明不可信 |
| Storage | ResultSet/Resolution/Bundle/Archive | migration、immutability、关系 | 状态恢复或数据一致性风险 |
| Acquisition | router/provider/materializer | fallback、partial、hash、path、max_bytes | 下载安全或资产真实性风险 |
| stdio E2E | 真实 MCP 子进程 | JSON-RPC、重启、幂等、恢复 | 协议链或进程边界风险 |
| OpenClaw E2E | 真实 Agent | Skill 发现、工具选择、状态延续、确认 | 最终用户链路风险 |
| Benchmark | 检索质量 | 相关性、Gap、早停、真实性 | 产品质量回退 |

## 12. 风险登记与处理策略

| 风险 | 触发信号 | 处理 |
| --- | --- | --- |
| Coverage 过严导致反复搜索 | Unnecessary Replan Rate 上升 | 用 benchmark 校准 required dimensions；探索型任务允许 search-only Present |
| LLM SemanticReview 不稳定 | 同一输入结果波动 | 限制枚举与理由结构；服务端事实不交给模型重算；必要时采用 deterministic prompt fixture |
| Registry scope 迁移破坏旧 Skill | Planner 读取失败/字段缺失 | 新增字段兼容；旧 acquire 保留一阶段并标 deprecated semantics |
| 真实平台反爬/接口变化 | network smoke 突然失败 | 平台 readiness 独立标记；不降低安全策略；失败不伪装整体无结果 |
| OpenClaw 环境版本变化 | doctor/probe schema 或配置行为变化 | 验收记录 OpenClaw/Node/模型版本；环境变化后重新跑真实 E2E |
| Fixture 与真实网络偏差 | fixture 通过、真实失败 | fixture 负责逻辑回归，network smoke 负责平台现实，两者不互相替代 |
| 文档再次漂移 | Schema/Runtime/Skill 描述冲突 | 增加 consistency tests；CURRENT_ARCHITECTURE 保持事实快照角色 |

## 13. 完成定义（Definition of Done）

当以下条件全部满足时，可以认为“主体架构阶段”结束，项目进入“稳定扩平台与持续质量优化”阶段：

1. 0017–0022 保持 completed；0023 的真实 OpenClaw 阻塞项关闭。
2. 0024 证明系统不会因为“有几个带标题的结果”就自动认为 Coverage 足够。
3. 0025 证明 Planner 能区分资源本体、representation、landing page、metadata。
4. 0026 证明真实 OpenClaw 能通过自然语言完成 Search -> Inspect -> Present -> Select -> Confirm -> Acquire -> Archive -> Recover。
5. 0027 建立可重复 benchmark，关键指标成为后续修改的发布门禁。
6. 当前公共 Tool 仍控制在 13 个；平台扩展继续通过 Adapter/Registry，而不是新增脚本型 Tool。
7. 所有能力边界都有机器事实、测试和文档三方一致性；未完成能力明确标 experimental/blocked/unsupported。

达到以上状态后，后续开发重点才适合切换到：新增/强化 Platform Adapter、Inspector、Downloader、Viewer 和生产部署，而不是继续修改核心骨架。
